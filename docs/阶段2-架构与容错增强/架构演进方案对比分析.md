# 架构演进方案对比分析

> 分析日期：2026-01-16
> 讨论背景：当前工程中维护了机械臂、AGV、外部轴、环境传感器、相机、gRPC等多个管理对象，需要评估架构合理性和故障应对方案

---

## 1. 问题背景

### 1.1 核心问题

当前工程中维护了多个管理对象：
- 机械臂控制器 (ArmController)
- AGV控制器 (AGVController)
- 外部轴控制器 (HTTP REST API)
- 环境传感器 (AirQualitySensor)
- 相机管理器 (CameraManager)
- gRPC通信 (StreamManager)

**关键疑问**：
1. 这些组件放在同一个工程/进程中维护是否合理？
2. 万一某一个服务挂掉了该如何应对？

---

## 2. 当前架构分析

### 2.1 现状

当前是**单体架构**，所有组件运行在同一个Python进程中：

```
RobotControlSystem (主进程)
├── TaskManager
│   └── RobotController
│       ├── AGVController      (TCP/IP)
│       ├── ArmController      (JAKA SDK + HTTP)
│       ├── CameraManager      (Orbbec + RTMP)
│       └── AirQualitySensor   (Modbus RTU)
├── gRPC StreamManager
└── TaskScheduler
```

### 2.2 优点

| 优点 | 说明 |
|-----|------|
| 部署简单 | 单进程、单配置文件 |
| 调试方便 | 所有日志在一起，便于排查问题 |
| 低延迟 | 进程内通信，无序列化开销 |
| 协调简单 | 统一状态管理，任务调度清晰 |

### 2.3 存在的问题

| 问题 | 影响 | 严重程度 |
|-----|------|---------|
| 单点故障 | 一个模块崩溃会拖垮整个系统 | 高 |
| 资源竞争 | 线程过多，GIL争用 | 中 |
| 耦合度高 | 某个硬件问题可能影响其他功能 | 高 |
| 难以单独升级 | 更新相机驱动需要重启整个系统 | 中 |

### 2.4 典型故障场景

| 故障场景 | 当前影响 |
|---------|---------|
| 相机驱动崩溃 | 整个进程可能卡死 |
| 环境传感器串口断开 | 读取线程异常，可能阻塞 |
| AGV TCP连接断开 | 移动命令失败，无自动恢复 |
| 机械臂SDK异常 | 操作无法执行，需重启系统 |
| gRPC连接断开 | 无法上报状态，任务无法接收 |

## 3. 方案一：增强当前架构的容错能力（推荐先做）

### 3.1 概述

**改动程度**：小
**实施周期**：1-2周
**风险**：低

不改变单体架构，通过增加防护机制来提升容错能力。

### 3.2 核心架构

```
┌─────────────────────────────────────────────────────────┐
│                   ComponentManager                       │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │HealthChecker│  │ RestartMgr  │  │ DegradeMgr  │     │
│  └─────────────┘  └─────────────┘  └─────────────┘     │
└─────────────────────────────────────────────────────────┘
          │                │                │
          ▼                ▼                ▼
┌─────────────────────────────────────────────────────────┐
│                   SafeController Wrapper                 │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │   AGV    │ │   Arm    │ │  Camera  │ │   Env    │   │
│  │ Wrapper  │ │ Wrapper  │ │ Wrapper  │ │ Wrapper  │   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘   │
└─────────────────────────────────────────────────────────┘
```

### 3.3 关键实现

#### 3.3.1 组件级健康检查和自动重启

```python
class ComponentManager:
    def __init__(self):
        self.components = {}  # name -> (instance, restart_func)
        self.health_status = {}

    def register(self, name, instance, restart_func):
        self.components[name] = (instance, restart_func)

    def health_check_loop(self):
        while True:
            for name, (instance, restart_func) in self.components.items():
                try:
                    if not instance.is_healthy():
                        self.restart_component(name, restart_func)
                except Exception as e:
                    logger.error(f"{name} health check failed: {e}")
                    self.restart_component(name, restart_func)
            time.sleep(5)

    def restart_component(self, name, restart_func):
        logger.warning(f"Restarting {name}...")
        try:
            restart_func()
            logger.info(f"{name} restarted successfully")
        except Exception as e:
            logger.error(f"Failed to restart {name}: {e}")
```

#### 3.3.2 每个控制器添加隔离wrapper

```python
class SafeController:
    def __init__(self, controller, name):
        self.controller = controller
        self.name = name
        self.failed = False

    def call(self, method, *args, **kwargs):
        if self.failed:
            logger.warning(f"{self.name} is in failed state, skipping")
            return None
        try:
            return getattr(self.controller, method)(*args, **kwargs)
        except Exception as e:
            logger.error(f"{self.name}.{method} failed: {e}")
            self.failed = True
            return None

    def reset(self):
        self.failed = False
```

#### 3.3.3 关键操作超时保护

```python
import concurrent.futures

def call_with_timeout(func, timeout=30, *args, **kwargs):
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
        future = executor.submit(func, *args, **kwargs)
        try:
            return future.result(timeout=timeout)
        except concurrent.futures.TimeoutError:
            logger.error(f"{func.__name__} timed out")
            return None
```

### 3.4 优缺点

**优点**：
- 改动最小，风险低
- 快速见效
- 不影响现有功能
- 可逐步增强

**缺点**：
- 仍然是单进程，无法完全隔离故障
- Python GIL 限制并发性能

## 4. 方案二：进程隔离（中等改动）

### 4.1 概述

**改动程度**：中
**实施周期**：3-4周
**风险**：中

将高风险组件隔离到独立进程，通过消息队列通信。

### 4.2 核心架构

```
主进程 (RobotControlSystem)
├── TaskManager & TaskScheduler
└── 通过消息队列与子进程通信

子进程1: AGVController
├── 独立TCP连接
└── 通过Redis/ZMQ与主进程通信

子进程2: ArmController
├── JAKA SDK + 外部轴HTTP
└── 通过Redis/ZMQ与主进程通信

子进程3: CameraManager
├── Orbbec驱动 + RTMP推流
└── 通过Redis/ZMQ与主进程通信

子进程4: 环境传感器
├── Modbus RTU
└── 通过Redis/ZMQ与主进程通信
```

### 4.3 通信架构图

```
┌─────────────────────────────────────────────────────────┐
│                    主进程                                │
│  ┌─────────────┐      ┌─────────────────────────────┐  │
│  │TaskManager  │ ←──→ │ ProcessManager              │  │
│  │TaskScheduler│      │ (监控子进程存活状态)          │  │
│  └─────────────┘      └─────────────────────────────┘  │
└────────────────────────────┬────────────────────────────┘
                             │
                    Redis/ZeroMQ 消息队列
                             │
         ┌───────────────────┼───────────────────┐
         │                   │                   │
         ▼                   ▼                   ▼
┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
│   AGV进程       │ │   Arm进程       │ │   Camera进程    │
│                 │ │                 │ │                 │
│ AGVController   │ │ ArmController   │ │ CameraManager   │
│ TCP/IP通信      │ │ JAKA SDK        │ │ Orbbec驱动      │
└─────────────────┘ └─────────────────┘ └─────────────────┘
```

### 4.4 关键实现

#### 4.4.1 子进程模板

```python
# controller_process.py - 子进程模板
import multiprocessing
import redis

class ControllerProcess(multiprocessing.Process):
    def __init__(self, controller_class, config, redis_url):
        super().__init__()
        self.controller_class = controller_class
        self.config = config
        self.redis_url = redis_url

    def run(self):
        controller = self.controller_class(self.config)
        redis_client = redis.Redis.from_url(self.redis_url)
        pubsub = redis_client.pubsub()
        pubsub.subscribe(f'{self.name}_commands')

        for message in pubsub.listen():
            if message['type'] == 'message':
                cmd = json.loads(message['data'])
                result = self.execute_command(controller, cmd)
                redis_client.publish(f'{self.name}_results', json.dumps(result))

    def execute_command(self, controller, cmd):
        try:
            method = getattr(controller, cmd['method'])
            return {'success': True, 'result': method(*cmd['args'])}
        except Exception as e:
            return {'success': False, 'error': str(e)}
```

#### 4.4.2 主进程管理器

```python
class ProcessManager:
    def __init__(self):
        self.processes = {}

    def start_controller(self, name, controller_class, config):
        p = ControllerProcess(controller_class, config, REDIS_URL)
        p.start()
        self.processes[name] = p

    def restart_if_dead(self):
        for name, p in self.processes.items():
            if not p.is_alive():
                logger.warning(f"{name} died, restarting...")
                self.start_controller(name, p.controller_class, p.config)
```

### 4.5 优缺点

**优点**：
- 故障隔离：一个进程崩溃不影响其他进程
- 可独立重启：无需重启整个系统
- 资源隔离：每个进程有独立的内存空间
- 绕过GIL：多进程可真正并行

**缺点**：
- 增加通信延迟（毫秒级）
- 需要引入消息队列（Redis/ZMQ）
- 调试复杂度增加
- 部署复杂度增加

## 5. 方案三：完整微服务化（大改动）

### 5.1 概述

**改动程度**：大
**实施周期**：2-3月
**风险**：高

将系统拆分为独立的微服务，每个服务可独立部署、扩展。

### 5.2 核心架构

```
┌──────────────────────────────────────────────┐
│           Backend Server (Cloud)              │
└─────────────────┬────────────────────────────┘
                  │ gRPC
┌─────────────────┴────────────────────────────┐
│    Robot Gateway (本地编排服务)               │
│    - 任务调度                                 │
│    - 状态聚合                                 │
│    - 故障协调                                 │
└───┬─────────┬─────────┬─────────┬───────────┘
    │         │         │         │
    ▼         ▼         ▼         ▼
┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐
│ AGV   │ │ Arm   │ │Camera │ │ Env   │
│Service│ │Service│ │Service│ │Service│
└───────┘ └───────┘ └───────┘ └───────┘
```

### 5.3 服务划分

| 服务 | 职责 | 通信方式 |
|-----|------|---------|
| Robot Gateway | 任务编排、状态聚合、对外通信 | gRPC (对外), HTTP (对内) |
| AGV Service | AGV导航控制 | HTTP REST API |
| Arm Service | 机械臂 + 外部轴控制 | HTTP REST API |
| Camera Service | 相机采集 + RTMP推流 | HTTP REST API |
| Env Service | 环境监测 | HTTP REST API |

class ServiceRegistry:

    def register(self, name, host, port):
        self.services[name] = {'host': host, 'port': port, 'healthy': True}

    def health_check(self):
        for name, info in self.services.items():
            try:
                resp = requests.get(f"http://{info['host']}:{info['port']}/health", timeout=5)

            except:
                info['healthy'] = False

### 5.6 优缺点

**优点**：
- 完全故障隔离
- 可独立扩展（如多相机）
- 技术栈可异构（Python/Go/Rust）
- 便于团队分工
- 支持多机器人协作

**缺点**：
- 部署复杂（Docker/K8s）
- 网络延迟增加
- 运维成本高
- 需要服务发现、负载均衡等基础设施
- 分布式系统调试困难

## 6. 方案对比

| 维度 | 方案一：容错增强 | 方案二：进程隔离 | 方案三：微服务化 |
|-----|----------------|----------------|----------------|
| 改动量 | 小（新增模块） | 中（重构通信） | 大（完全重构） |
| 实施周期 | 1-2周 | 3-4周 | 2-3月 |
| 故障隔离 | 部分（线程级） | 较好（进程级） | 完全（服务级） |
| 部署复杂度 | 无变化 | 略增加 | 大幅增加 |
| 运维复杂度 | 略增加 | 中等增加 | 大幅增加 |
| 性能影响 | 无 | 毫秒级延迟 | 毫秒级延迟 |
| 可扩展性 | 一般 | 较好 | 很好 |
| 适用场景 | 单机器人 | 单机器人 | 多机器人/云端 |

## 7. 实施建议

### 7.1 推荐路线

```
第一阶段（当前可做）        第二阶段（问题频繁时）      第三阶段（规模化时）
      │                          │                        │
      ▼                          ▼                        ▼
┌─────────────┐           ┌─────────────┐          ┌─────────────┐
│  方案一      │    ──→    │  方案二      │   ──→    │  方案三      │
│  容错增强    │           │  进程隔离    │          │  微服务化    │
│             │           │             │          │             │
│ • 健康检查   │           │ • 相机隔离   │          │ • 容器化     │
│ • 超时保护   │           │ • 传感器隔离 │          │ • 服务发现   │
│ • 自动恢复   │           │ • 消息队列   │          │ • 多机器人   │
│ • 优雅降级   │           │ • 进程监控   │          │ • 云端部署   │
└─────────────┘           └─────────────┘          └─────────────┘
```

### 7.2 第一阶段具体任务

1. **添加组件级健康检查**
   - 为每个控制器添加 `is_healthy()` 方法
   - 创建 HealthChecker 定期检查

2. **添加超时保护**
   - 所有硬件调用添加超时机制
   - 超时后返回默认值，不阻塞系统

3. **添加优雅降级**
   - 某组件失败时，标记状态但不影响其他组件
   - 核心功能（AGV、机械臂）优先保障

4. **增强日志和监控**
   - 记录每个组件的健康状态
   - 添加故障告警机制

### 7.3 第二阶段触发条件

当出现以下情况时，考虑实施方案二：

- 相机驱动频繁崩溃（>1次/天）
- 环境传感器导致主进程阻塞
- 需要独立更新某个组件
- 单个组件占用过多资源

### 7.4 第三阶段触发条件

当出现以下需求时，考虑实施方案三：

- 需要支持多机器人协作
- 需要云端部署和管理
- 需要不同技术栈（如用Go重写性能敏感模块）
- 团队规模扩大，需要服务化分工

## 8. 总结

### 8.1 针对问题的回答

**Q1: 放在同一个工程是否合理？**

对于单机器人场景，目前的单体架构是合理的：
- 优点是简单、低延迟、易于协调
- 但需要增加容错机制来提升稳定性

**Q2: 某个服务挂掉如何应对？**

- **短期**：实施方案一，增加健康检查、自动恢复、优雅降级
- **中期**：如果问题频繁，将高风险组件隔离到子进程
- **长期**：如果需要规模化，考虑微服务化

### 8.2 建议优先级

1. **立即实施方案一**（改动小、见效快）
2. **观察运行情况**，按需推进方案二
3. **方案三作为长期演进方向**
