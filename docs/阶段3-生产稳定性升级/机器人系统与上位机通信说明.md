# 机器人系统与上位机通信说明

> 核对日期：2026-08-27  
> 说明范围：以当前工程实际代码为准，区分“协议已定义”和“程序当前实际使用”。  
> 上位机：本文指实现 `RobotService` gRPC 服务的后台/管理端。

## 1. 通信概览

机器人进程作为 gRPC 客户端，主动连接上位机，并长期维持两条双向流：

```text
机器人端                                              上位机

RobotUploadRequest    ── clientUpload ──────────────> 上传状态和环境数据
RobotUploadResponse   <─ clientUpload ─────────────── 确认上传结果

ClientStreamMessage   ── serverCommand ─────────────> 心跳、命令状态、任务进度、操作结果
ServerStreamMessage   <─ serverCommand ────────────── 下发任务和控制命令
```

| 项目 | 当前实现 |
| --- | --- |
| 协议 | gRPC + Protocol Buffers，HTTP/2 双向流 |
| 服务 | `RobotService` |
| 上位机地址 | 默认读取 `conf/config.json`，当前配置为 `192.168.8.14:9898` |
| 机器人标识 | `robot_id`，当前配置为 `12345` |
| 连接发起方 | 机器人端 |
| 通道安全 | 当前使用 `grpc.insecure_channel`，没有 TLS 和应用层鉴权 |
| 时间字段 | Unix 毫秒时间戳 |
| 断线处理 | 自动重连，并将未发送消息保存到 SQLite 离线队列 |

## 2. 两条双向流

| RPC | 机器人发送 | 上位机返回 | 主要用途 |
| --- | --- | --- | --- |
| `clientUpload` | `RobotUploadRequest` | `RobotUploadResponse` | 周期上传机器人状态、位置、任务和环境数据 |
| `serverCommand` | `ClientStreamMessage` | `ServerStreamMessage` | 上位机下发命令；机器人返回心跳、命令状态、任务进度、操作结果和硬件状态 |

两条流启动成功后，系统才将连接状态设置为 `CONNECTED`。任何一条流断开都会触发重连流程。

## 3. 通用字段约定

### 3.1 上传消息 `RobotUploadRequest`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `msg_id` | `int64` | 上传消息唯一标识 |
| `msg_time` | `int64` | 消息产生时间，毫秒 |
| `msg_type` | `MsgType` | `ROBOT_STATUS` 或 `ENVIRONMENT_DATA` |
| `robot_id` | `int64` | 机器人标识 |
| `position_info` | `PositionInfo` | AGV、机械臂和外部轴位置 |
| `task_info` | `TaskInfo` | 当前任务快照，无任务时发送空任务 |
| `data_json` | `oneof` | `robot_status` 或 `environment_data` |

### 3.2 上位机命令 `ServerStreamMessage`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `command_id` | `int64` | 命令唯一标识，也是后续响应的关联键 |
| `command_time` | `int64` | 命令产生时间，毫秒 |
| `command_type` | `CmdType` | 命令类型 |
| `robot_id` | `int64` | 目标机器人标识 |
| `data_json` | `oneof` | 与命令类型匹配的命令参数；Trigger 命令可为空 |

### 3.3 机器人命令通道响应 `ClientStreamMessage`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `command_id` | `int64` | 原命令 ID，心跳则为机器人生成的 ID |
| `command_time` | `int64` | 响应产生时间，毫秒 |
| `command_type` | `ClientMessageType` | 响应类别，不是上位机命令的 `CmdType` |
| `robot_id` | `int64` | 机器人标识 |
| `data_json` | `oneof` | 对应的响应内容 |

## 4. 机器人向上位机发送的内容

### 4.1 `clientUpload`：周期上报

#### 4.1.1 机器人状态 `ROBOT_STATUS`

- 周期：每 10 秒。
- 外层携带当前位置和当前任务快照。
- `robot_status` 携带电池、移动/连接/急停状态。

| 数据块 | 字段 | 当前含义 |
| --- | --- | --- |
| `position_info` | `AGVPositionInfo` | `[x, y, theta]` |
| `position_info` | `ARMPositionInfo` | 六个机械臂关节位置 |
| `position_info` | `EXTPositionInfo` | 四个外部轴位置 |
| `task_info` | `inspection_task_list` | 当前任务、站点、任务状态及时间信息 |
| `battery_info` | `power_percent` | AGV 剩余电量 |
| `battery_info` | `charge_status` | 当前发送 `charging` 或 `discharging` |
| `system_status` | `move_status` | `IDLE/RUNNING/SUCCEEDED/FAILED/CANCELED/UNKNOWN` |
| `system_status` | `is_connected` | 当前构造上报时固定为 `true` |
| `system_status` | `soft_estop_status` | AGV 软急停状态 |
| `system_status` | `hard_estop_status` | AGV 硬急停状态 |
| `system_status` | `estop_status` | 综合急停状态 |
| `error_info` | `code/level/message` | Proto 支持，但当前周期上报没有填充 |

无正在执行的任务时，仍会发送 `task_info`，其中任务 ID 转换为 `0`、站点列表为空、状态为待执行。

#### 4.1.2 环境数据 `ENVIRONMENT_DATA`

- 周期：每 30 秒。
- 同样携带当前 `position_info` 和 `task_info`。
- `environment_data.sensor_data` 包含：

| 字段 | 含义 |
| --- | --- |
| `temperature` | 温度 |
| `humidity` | 湿度 |
| `oxygen` | 氧气浓度 |
| `carbonDioxide` | 二氧化碳浓度；Python 内部字段名为 `carbon_dioxide` |
| `pm25` | PM2.5 |
| `pm10` | PM10 |
| `etvoc` | eTVOC |
| `noise` | 噪声 |

#### 4.1.3 上位机对上传消息的响应

上位机通过同一条 `clientUpload` 流返回 `RobotUploadResponse`：

```text
msg_id + msg_time + msg_type + robot_id
data_json.code
data_json.info
```

上位机应回传可与上传消息关联的 `msg_id`。机器人会将收到的响应保存到数据库，但当前业务流程不依赖该响应决定动作是否成功。

### 4.2 `serverCommand`：机器人返回的消息

| `ClientMessageType` | 数值 | 触发条件 | 主要内容 |
| --- | ---: | --- | --- |
| `HEARTBEAT` | 0 | 每 30 秒 | `response_info.code="0"`、`info="heartbeat"` |
| `COMMAND_RESPONSE` | 1 | 协议预留 | 当前主流程没有发送通用命令响应 |
| `SET_MARKER_RESPONSE` | 2 | 设置标记点命令成功后 | AGV、机械臂、外部轴当前位置 |
| `COMMAND_STATUS_UPDATE` | 3 | 普通调度命令状态变化 | 命令类型、状态、消息、时间、重试次数 |
| `TASK_PROGRESS_UPDATE` | 4 | 任务站点开始、阶段变化、站点完成 | 任务/站点状态、当前执行阶段和说明 |
| `OPERATION_RESULT` | 5 | 开门、关门、拍照或服务操作完成 | 成功/失败、图片、设备、门禁、耗时 |
| `HARDWARE_STATUS_RESPONSE` | 6 | 处理硬件启动/关闭命令后 | 三个硬件模块的实际启用状态和说明 |

#### 4.2.1 命令状态更新

普通命令进入统一调度器后，可能依次发送：

```text
QUEUED → RUNNING → COMPLETED
                 ↘ RETRYING → RUNNING ...
                 ↘ FAILED
```

`CommandStatusUpdate` 字段：

- `command_id`
- `command_type`：原始 `CmdType`
- `status`：`PENDING/QUEUED/RUNNING/COMPLETED/FAILED/CANCELLED/RETRYING`
- `message`
- `timestamp`
- `retry_count`

硬件启动和硬件关闭命令绕过统一调度器，因此不会发送上述状态序列，只返回 `HARDWARE_STATUS_RESPONSE`。

#### 4.2.2 任务进度更新

`TaskProgressUpdate` 包含：

- 任务 ID、名称和任务状态；
- 总站点数、已完成站点数、失败站点数；
- 当前站点 ID、名称和状态；
- 当前执行阶段 `current_station_phase`；
- 当前阶段说明 `current_station_detail`；
- 进度文字和毫秒时间戳。

当前站点阶段值：

```text
pending
agv_moving
arm_positioning
ext_positioning
operating
completed
failed
```

#### 4.2.3 操作结果

`OperationResult` 用于站点内的业务操作：

| 操作 | 关键返回字段 |
| --- | --- |
| `OPEN_DOOR` | `status`、`message`、`door_ip`、`duration` |
| `CLOSE_DOOR` | `status`、`message`、`door_ip`、`duration` |
| `CAPTURE` | `status`、`message`、`device_id`、`image_base64[]`、`duration` |
| `SERVICE` | `status`、`message`、`duration` |

所有操作结果还带有 `task_id`、`station_id` 和 `timestamp`。

#### 4.2.4 硬件状态响应

`HardwareStatusResponse` 返回操作后的状态：

- `robot_enabled`：机器人模块（AGV + 机械臂控制器）是否启用；
- `camera_enabled`：相机是否启用；
- `env_sensor_enabled`：环境传感器是否启用；
- `message`：每个被操作模块的执行结果说明。

## 5. 上位机向机器人下发的内容

| `CmdType` | 数值 | 参数 | 当前机器人行为 | 返回内容 |
| --- | ---: | --- | --- | --- |
| `RESPONSE_CMD` | 0 | `response_info` | 保存后忽略，视为上位机确认消息 | 无 |
| `ROBOT_MODE_CMD` | 1 | `robot_mode_command.robot_mode` | 更新 `current_mode`，进入调度器后再次记录模式切换 | 命令状态更新 |
| `TASK_CMD` | 2 | `task_cmd` | 解析并按站点顺序执行巡检任务 | 命令状态、任务进度、操作结果、周期状态 |
| `JOY_CONTROL_CMD` | 3 | `angular_velocity`、`linear_velocity` | 调用 AGV 摇杆控制 | 命令状态更新 |
| `SET_MARKER_CMD` | 4 | `marker_name` | 将 AGV 当前位置设置为命名标记点 | 命令状态；成功后额外返回当前位置 |
| `CHARGE_CMD` | 5 | 无，Trigger 信号 | 调用机器人充电流程 | 命令状态更新 |
| `POSITION_ADJUST_CMD` | 6 | 无，Trigger 信号 | 使用固定标记 `charge_point_1F_6010` 执行位置调整 | 命令状态更新 |
| `HEARTBEAT_CMD` | 7 | 协议未规定载荷 | Proto 已定义，但当前 Python 命令模型未实现，实际会按 `RESPONSE_CMD` 忽略 | 无 |
| `HARDWARE_START_CMD` | 8 | `hardware_control_cmd` | 直接启动选中的硬件模块 | 硬件状态响应 |
| `HARDWARE_SHUTDOWN_CMD` | 9 | `hardware_control_cmd` | 直接关闭选中的硬件模块 | 硬件状态响应 |

### 5.1 机器人模式

Proto 定义：

```text
INSPECTION / SERVICE / JOY_CONTROL / ESTOP / CHARGE / STAND_BY / CONFIGURATION
```

当前转换代码明确映射前五项；`STAND_BY` 依靠默认值得到待命模式；`CONFIGURATION` 当前也会退化为 `STAND_BY`。模式命令目前主要更新软件状态和日志，没有调用底层控制器改变硬件模式。

### 5.2 巡检任务

任务主要字段：

- `task_id`、`task_name`、`robot_mode`、`generate_time`；
- `station_list[]`。

每个站点主要字段：

- `station_id`、`sort`、`name`；
- `agv_marker`：AGV 目标标记点；
- `robot_pos[]`：六轴机械臂目标位置；
- `ext_pos[]`：四个外部轴目标位置；
- `operation_config`：操作类型、门禁 IP、设备 ID。

站点按照 `sort` 升序执行。执行链路为：

```text
AGV 导航
  → 机械臂定位（有 robot_pos 时）
  → 外部轴定位（有 ext_pos 时）
  → 开门/关门/拍照/服务（不是 NONE 时）
  → 头部动作
  → 站点完成
```

站点失败会按照机器人端默认配置重试；当前从上位机下发的 `Station.max_retries` 没有被采用，转换为内部任务时固定为 3 次重试。

### 5.3 摇杆控制

Proto 中 `angular_velocity` 和 `linear_velocity` 是字符串；机器人收到后转换为浮点数，空字符串按 `0.0` 处理。

### 5.4 硬件控制

`HardwareControlCommand` 的布尔值表示“是否操作该模块”，不是目标状态：

```text
HARDWARE_START_CMD    + robot=true  → 启动机器人模块
HARDWARE_SHUTDOWN_CMD + robot=true  → 关闭机器人模块
robot=false                         → 不操作机器人模块
```

三个字段都为 `false` 时不会改变硬件，但当前实现仍会返回一次实际硬件状态，可作为无副作用的状态查询方式；协议中尚未定义独立的硬件状态查询命令。

## 6. 典型通信时序

### 6.1 启动与连接

```text
机器人启动
  → 建立 insecure gRPC Channel
  → 打开 clientUpload 双向流
  → 打开 serverCommand 双向流
  → 注册响应处理器
  → 每 10 秒上传机器人状态
  → 每 30 秒上传环境数据
  → 每 30 秒在 serverCommand 流发送心跳
```

### 6.2 巡检任务

```text
上位机  → TASK_CMD
机器人  → COMMAND_STATUS_UPDATE(QUEUED)
机器人  → COMMAND_STATUS_UPDATE(RUNNING)
机器人  → TASK_PROGRESS_UPDATE(站点及阶段变化，多次)
机器人  → OPERATION_RESULT(有业务操作时)
机器人  → COMMAND_STATUS_UPDATE(COMPLETED/FAILED)
```

周期性的 `ROBOT_STATUS` 和 `ENVIRONMENT_DATA` 与上述任务消息并行发送。

## 7. 断线、重连和离线消息

当前连接策略：

- 初次连接超时：10 秒；
- 任一流断开后进入自动重连；
- 指数退避：2、4、8、16、30、30……秒，没有最大尝试次数；
- 心跳超时阈值：60 秒；
- 离线消息存入 SQLite；
- 离线队列上限：10,000 条；
- 离线消息有效期：24 小时；
- 重连后每批发送 10 条，批次间隔 0.1 秒。

需要注意：`send_message()` 返回成功只表示消息已进入本地发送队列，不代表上位机已经处理。当前数据库中的 `sent` 状态也是“已提交发送”的含义，不是端到端业务确认。

## 8. 当前硬件数据来源

当前配置 `use_mock=false`，因此系统使用真实 `RobotController` 主流程，但当前工作区已做局部 Mock 替换：

| 数据/功能 | 当前来源 |
| --- | --- |
| AGV 位置、电量、移动和急停状态 | 真实 `AGVController` |
| 机械臂六轴位置 | `MockArmController` 虚拟缓存 |
| 外部轴四轴位置 | `MockArmController` 虚拟缓存 |
| 头部动作 | `MockArmController` 模拟成功 |
| 环境八项数据 | `MockAirQualitySensor` 固定模拟数据 |
| 相机图片 | 真实 `CameraManager`，前提是相机模块可用 |

因此，上位机收到机械臂、外部轴和环境数据并不代表对应真实硬件已经恢复。

## 9. 当前实现与协议的差异及联调注意事项

以下内容是根据当前代码确认的实际情况：

1. **没有 TLS 或鉴权**：通信使用明文 `insecure_channel`，应确保网络隔离；跨不可信网络部署前需要补充 TLS 和身份认证。
2. **上位机 `HEARTBEAT_CMD` 未实现**：Proto 中存在该命令，但 Python `CmdType` 和转换器没有对应项，收到后会退化为 `RESPONSE_CMD` 并被忽略。
3. **通用 `COMMAND_RESPONSE` 未发送**：普通命令使用 `COMMAND_STATUS_UPDATE` 作为接收和执行状态反馈。
4. **`clientUpload` 空闲心跳构造存在字段不匹配**：代码尝试把 `position_info` 放入 `RobotStatusUpload`，但该字段属于外层 `RobotUploadRequest`；异常被 DEBUG 日志捕获。正常情况下每 10 秒的状态上报仍会维持该流活动。
5. **上传响应内容没有完整入库**：当前处理器直接检查 `RobotUploadResponse.code/info`，实际字段位于 `response.data_json.code/info`，所以数据库通常只能保存响应 `msg_id`。
6. **成功的站点操作结果可能重复上报**：操作执行后触发一次结果回调，站点完成回调又会从 metadata 再触发一次；失败操作通常只上报一次。
7. **模式切换不控制底层硬件**：当前只更新软件模式并记录日志；`CONFIGURATION` 还会被映射为 `STAND_BY`。
8. **任务部分完成会映射为完成**：内部 `PARTIAL_COMPLETED` 在 Proto 中映射为 `TASK_STATUS_COMPLETED`，上位机需结合失败站点数判断是否部分失败。
9. **消息 ID 存在两种表示**：机器人周期消息先生成 UUID 字符串，转成 Proto 时通过 Python `hash()` 压缩为正整数；数据库中的 UUID 与线上 `msg_id` 不相同。上位机下发命令应优先使用正整数 ID。
10. **心跳监控不是业务 ACK 监控**：流的 `last_activity` 在本地消息出队时也会更新，因此“未超时”不等价于上位机业务已经成功处理消息。
11. **任务下发字段不是全部采用**：当前主要读取任务基本信息和 `StationConfig`；上位机传入的站点状态、metadata、时间字段及 `max_retries` 不会完整保留。
12. **最终任务状态不一定通过任务进度消息送达**：最后一个站点完成时会发送进度，但此时任务状态通常仍是 `RUNNING`；随后任务才更新为 `COMPLETED/PARTIAL_COMPLETED/FAILED`，当前没有为该变化单独触发一次 `TASK_PROGRESS_UPDATE`。上位机应同时参考最终 `COMMAND_STATUS_UPDATE`，后续建议补发最终任务进度。

## 10. 联调验收建议

上位机联调至少验证以下闭环：

1. 两条双向流均能建立且断线后能重连。
2. 连续接收至少 3 次 `ROBOT_STATUS`，间隔约 10 秒。
3. 连续接收至少 2 次 `ENVIRONMENT_DATA`，间隔约 30 秒。
4. 接收机器人 `HEARTBEAT`，间隔约 30 秒。
5. 下发一个无运动风险的模式命令，确认收到 `QUEUED/RUNNING/COMPLETED`。
6. 下发硬件命令且三个布尔值均为 `false`，确认收到 `HARDWARE_STATUS_RESPONSE`。
7. 下发测试任务，确认命令状态、任务阶段、操作结果和最终状态能用同一 `command_id` 关联。
8. 断开上位机网络后恢复，确认离线消息被补发且没有无限重复。
9. 对拍照结果验证 Base64 数量、单条消息大小和上位机存储限制。
