# 外包需求文档 - 机器人控制系统稳定性升级项目

---

## 一、项目背景

### 1.1 项目简介

我们有一套基于Python开发的机器人控制系统（Lumi），用于控制巡检机器人完成自动化巡检任务。系统包含：
- AGV小车（自动导航）
- 机械臂（6个关节）
- 外部轴（4个关节）
- 摄像头和环境传感器

机器人通过gRPC与后台服务器通信，接收任务指令并上报状态。

### 1.2 当前痛点

系统即将部署到生产环境，需要7×24小时无人值守运行，但当前存在以下问题：

| 问题 | 影响 | 紧迫程度 |
|------|------|---------|
| ❌ 网络断开后无法自动重连 | 失联后需人工重启，无法无人值守 | 🔴 高 |
| ❌ 启动后硬件立即运行 | 无法远程控制启停，缺乏灵活性 | 🔴 高 |
| ❌ 断线期间数据丢失 | 任务执行情况无法追溯 | 🔴 高 |
| ❌ 软件异常崩溃后需人工重启 | 无法无人值守，影响连续运行 | 🔴 高 |

## 二、核心需求（按优先级）

### 🔴 需求1: gRPC自动重连机制 [P0 - 必须完成]

**需求描述**:
当机器人与服务器的网络连接断开后，能自动重连并恢复通信，无需人工干预。

**具体要求**:
1. 实现心跳检测，每30秒发送一次心跳
2. 检测到连接断开后，自动重连（重试间隔：2秒、4秒、8秒...最大30秒）
3. 断线期间的消息缓存到本地，重连后发送
4. 断线期间正在执行的任务继续执行，重连后同步任务状态

**验收标准**:
- [ ] 手动关闭服务端后，30秒内客户端开始重连
- [ ] 服务端重启后，客户端自动连接成功
- [ ] 断线期间发送的100条状态消息在重连后全部送达
- [ ] 断线期间执行的任务，重连后服务端能看到完整结果

**工作量估算**: 2天

---

### 🔴 需求2: 启动流程分阶段控制 [P0 - 必须完成]

**需求描述**:
将系统启动分为3个独立阶段，可分别控制，不再是启动即运行硬件。

**具体要求**:

**当前流程** (❌ 不符合需求):
```
启动程序 → 自动连接gRPC → 自动启动AGV/机械臂/外部轴 → 开始工作
```

**目标流程** (✅ 符合需求):
```
阶段1: 启动程序 → 自动连接gRPC → 等待指令
阶段2: 收到服务端指令 → 启动指定硬件模块 → 硬件进入就绪状态
阶段3: 收到任务指令 → 执行任务
```


**新增代码接口**:
```python
# RobotControlSystem新增方法
system.start_communication()     # 阶段1: 仅启动gRPC通信
system.start_task_manager()      # 阶段2: 初始化任务管理（不启动硬件）
```
当前需求范围内需修改 `RobotService.proto`，在enum CmdType 中新增硬件启动和硬件关闭指令
```protobuf
enum CmdType {
   ……
    HEARTBEAT_CMD = 7; // 心跳确认
    HARDWARE_START_CMD = 8; // 硬件启动命令
    HARDWARE_SHUTDOWN_CMD = 9; // 硬件关闭命令
}
```

**验收标准**:
- [ ] 程序启动后，gRPC连接成功，但AGV/机械臂/外部轴未启动
- [ ] 可以与服务端正常通信，接收和发送消息
- [ ] 硬件模块不会自动启动，必须等待服务端命令

**工作量估算**: 3天

---

### 🔴 需求3: 断线数据持久化和同步 [P0 - 必须完成]

**需求描述**:
断线期间机器人继续执行任务，重连后将断线期间的状态和数据同步到服务端。

**具体要求**:

1. **新增数据库表**（SQLite）:
   - `offline_messages`: 存储断线期间未发送的消息
   - `task_execution_snapshot`: 存储任务执行快照
   - `system_state`: 存储系统状态（连接状态、硬件状态等）

2. **断线期间行为**:
   - 正在执行的任务继续执行
   - 定期保存任务进度快照（每个站点完成后保存）
   - 要发送的状态消息保存到数据库

3. **重连后行为**:
   - 读取断线期间的消息和快照
   - 批量发送到服务端（限速，避免流量激增）
   - 发送任务执行结果和最终状态

4. **程序重启行为**（按用户要求）:
   - 清空所有未完成的任务
   - 清空硬件状态（所有硬件恢复到未启动状态）
   - 等待服务端重新下发指令

**验收标准**:
- [ ] 执行任务时断线，任务继续执行到完成
- [ ] 重连后，服务端收到任务的完整执行记录（每个站点的状态）
- [ ] 断线期间要发送的100条消息在重连后全部送达
- [ ] 重启程序后，数据库中未完成的任务状态变为CANCELLED

**工作量估算**: 3天

### 🔴 需求4: 健康监控和异常恢复 [P0 - 必须完成]

**需求描述**:
系统能自动检测异常并尝试恢复，减少人工干预。

**具体要求**:

1. **健康检查**（每30秒）:
   - 检查gRPC连接状态
   - 检查各硬件子系统状态
   - 检查电池电量
   - 检查任务执行异常

2. **异常类型和处理策略**:
   | 异常类型 | 处理策略 | 示例 |
   |---------|---------|------|
   | 连接断开 | 自动重连 | gRPC连接丢失 |
   | 硬件初始化失败 | 重试3次，失败后报警 | AGV连接超时 |
   | 任务执行失败 | 重试3次，继续下一站点 | 机械臂运动超时 |
   | 电量低 | 主动上报，等待充电指令 | 电量<20% |

3. **异常上报**:
   - 发生异常时立即上报到服务端
   - 包含错误码、错误信息、恢复状态

**验收标准**:
- [ ] 系统每30秒进行一次健康检查
- [ ] 检测到AGV异常后，自动重试3次，失败后上报
- [ ] 检测到电量低于20%时，上报警告消息
- [ ] 连接断开后自动触发重连流程

**工作量估算**: 2天

---

### 🔴 需求5: 软件服务化——异常崩溃自动重启 [P0 - 必须完成]

**需求描述**:
将机器人控制系统注册为本地服务（Windows使用NSSM，Linux使用systemd），实现软件异常崩溃后自动重启，保证无人值守连续运行。

**具体要求**:

1. **Windows平台**:
   - 使用NSSM（Non-Sucking Service Manager）将 `RobotControlSystem.py` 注册为Windows服务
   - 配置崩溃后自动重启策略（重启延迟：5秒，最大重试次数：不限）
   - 提供安装和卸载服务的脚本（`install_service.bat` / `uninstall_service.bat`）

2. **Linux平台**:
   - 创建systemd service unit文件（`.service`）
   - 配置 `Restart=always`、`RestartSec=5`
   - 提供 `enable` / `disable` / `status` 管理脚本

3. **启动与恢复衔接**:
   - 服务重启后，系统自动进入阶段1（仅连接gRPC，等待指令），与需求2衔接
   - 重启前的未完成任务按需求3的规则处理（清空未完成任务，等待服务端重新下发）

4. **日志与监控**:
   - 服务管理器的重启事件需可查询（NSSM日志 / systemd journal）
   - 崩溃前的应用日志需保留（配合 `logs/` 目录的滚动日志），便于排查

**验收标准**:
- [ ] Windows环境：强制终止进程后，服务自动在5秒内重启
- [ ] Linux环境：强制终止进程后，systemd自动在5秒内重启
- [ ] 重启后系统正常连接gRPC并进入等待状态
- [ ] 连续模拟5次崩溃，每次均能自动恢复
- [ ] 安装/卸载脚本执行无误，提供使用文档

**工作量估算**: 2天

## 三、技术说明

### 3.1 技术栈

| 组件 | 技术 |
|------|------|
| 语言 | Python 3.8+ |
| 通信 | gRPC (双向流) |
| 数据库 | SQLite |
| 机械臂SDK | JAKA SDK (已集成) |
| AGV通信 | TCP/IP Socket (已实现) |
| 外部轴控制 | HTTP REST API (已实现) |
| 服务管理 | NSSM (Windows) / systemd (Linux) |
