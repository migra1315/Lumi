# 数据库优化修改方案

## 一、问题分析

### 1.1 robot_sent_messages 表为空的原因

经过代码分析，发现 `robot_sent_messages` 表为空是因为**只有部分消息发送函数调用了数据库保存方法**。

#### 当前消息发送函数及数据库保存情况

| 函数名 | 位置 | 消息类型 | 发送流 | 是否保存到DB |
|--------|------|---------|--------|------------|
| `_send_message()` | RobotControlSystem.py:467 | ROBOT_STATUS/ENVIRONMENT_DATA | clientUpload | ✅ 已保存 |
| `_send_command_status_update()` | RobotControlSystem.py:559 | COMMAND_STATUS_UPDATE | serverCommand | ❌ **未保存** |
| `_send_set_marker_response()` | RobotControlSystem.py:621 | SET_MARKER_RESPONSE | serverCommand | ❌ **未保存** |
| `_send_task_progress_update()` | RobotControlSystem.py:667 | TASK_PROGRESS_UPDATE | serverCommand | ❌ **未保存** |
| `_send_operation_result()` | RobotControlSystem.py:761 | OPERATION_RESULT | serverCommand | ❌ **未保存** |

**根本原因**：通过 `serverCommand` 流发送的 4 个函数都没有调用 `save_sent_message()` 方法。

### 1.2 数据库表分析结论

#### 现有表结构（共 8 张表）

| 表名 | 用途 | 当前使用状态 | 分析结论 |
|------|------|-------------|----------|
| `tasks` | 任务主表 | ❌ **废弃** | `save_task()` 已被注释（TaskManager.py:257） |
| `station_tasks` | 站点任务表 | ❌ **废弃** | 随 `save_task()` 一起写入，同样无数据 |
| `task_history` | 任务执行历史 | ✅ 正常使用 | `log_task_action()` 被多处调用 |
| `robot_received_messages` | 接收消息表 | ✅ 正常使用 | 存储从服务器收到的命令 |
| `robot_sent_messages` | 发送消息表 | ⚠️ **数据为空** | 部分发送函数未调用保存方法 |
| `unified_commands` | 统一命令表 | ✅ 正常使用 | 当前任务管理的主表 |
| `environment_data_history` | 环境数据历史 | ✅ 正常使用 | 环境传感器数据历史 |
| `system_config` | 系统配置表 | ✅ 正常使用 | 系统配置键值对 |

#### 废弃表详细分析

**`tasks` 和 `station_tasks` 表已废弃，原因如下：**

1. **`save_task()` 已被注释**（TaskManager.py:257）：
   ```python
   # # 同时保存到tasks表（兼容性）
   # self.database.save_task(task)
   ```

2. **虽然更新方法仍被调用，但无效**：
   - `update_task_status()` 在 TaskScheduler.py:290 被调用
   - `update_station_task_status()` 在 TaskScheduler.py 多处被调用（374, 375, 423, 453, 565）
   - `add_station_retry_count()` 在 TaskScheduler.py:374 被调用
   - **但由于没有 `save_task()` 写入数据，这些 UPDATE 操作不会影响任何记录**

3. **当前任务管理使用 `unified_commands` 表**，`tasks` 和 `station_tasks` 是旧设计遗留

**建议**：删除 `tasks` 和 `station_tasks` 表及相关方法，避免代码混淆。

## 二、数据流与消息表设计

### 2.1 系统数据流架构

系统有两个 gRPC 双向流，每个流都有上传和下载两个方向：

```
┌─────────────────────────────────────────────────────────────────┐
│                        gRPC 通信架构                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                   clientUpload 流                        │   │
│  │  机器人 ──发送──> 服务器：状态、环境数据等                   │   │
│  │  机器人 <──接收── 服务器：上传响应/确认                     │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                  serverCommand 流                        │   │
│  │  机器人 <──接收── 服务器：任务命令、模式切换等               │   │
│  │  机器人 ──发送──> 服务器：命令状态、任务进度、操作结果       │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 四表消息管理方案

按照两个数据流的上传/下载方向，设计 4 张独立的消息表：

| 表名 | 数据流 | 方向 | 存储内容 |
|------|--------|------|----------|
| `client_upload_sent` | clientUpload | 发送 | 机器人上传的状态、环境数据 |
| `client_upload_received` | clientUpload | 接收 | 服务器对上传的响应（如有） |
| `server_command_received` | serverCommand | 接收 | 服务器下发的命令 |
| `server_command_sent` | serverCommand | 发送 | 机器人发送的命令响应 |

#### 表结构设计

##### 1. `client_upload_sent` - clientUpload 流发送的消息

```sql
CREATE TABLE IF NOT EXISTS client_upload_sent (
    msg_id TEXT PRIMARY KEY,
    msg_time INTEGER NOT NULL,           -- 消息时间戳（毫秒）
    msg_type TEXT NOT NULL,              -- 消息类型：ROBOT_STATUS, ENVIRONMENT_DATA
    robot_id TEXT NOT NULL,
    data_json TEXT NOT NULL,             -- 消息数据 JSON
    status TEXT DEFAULT 'sent',          -- 状态：pending, sent, ack, failed
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_client_upload_sent_time ON client_upload_sent(msg_time);
CREATE INDEX IF NOT EXISTS idx_client_upload_sent_type ON client_upload_sent(msg_type);
```

##### 2. `client_upload_received` - clientUpload 流接收的响应

```sql
CREATE TABLE IF NOT EXISTS client_upload_received (
    msg_id TEXT PRIMARY KEY,
    msg_time INTEGER NOT NULL,           -- 消息时间戳（毫秒）
    msg_type TEXT NOT NULL,              -- 响应类型
    robot_id TEXT NOT NULL,
    data_json TEXT NOT NULL,             -- 响应数据 JSON
    processed BOOLEAN DEFAULT FALSE,     -- 是否已处理
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_client_upload_received_time ON client_upload_received(msg_time);
CREATE INDEX IF NOT EXISTS idx_client_upload_received_processed ON client_upload_received(processed);
```

##### 3. `server_command_received` - serverCommand 流接收的命令

```sql
CREATE TABLE IF NOT EXISTS server_command_received (
    msg_id TEXT PRIMARY KEY,
    msg_time INTEGER NOT NULL,           -- 消息时间戳（毫秒）
    cmd_type TEXT NOT NULL,              -- 命令类型：TASK_CMD, ROBOT_MODE_CMD 等
    robot_id TEXT NOT NULL,
    data_json TEXT NOT NULL,             -- 命令数据 JSON
    processed BOOLEAN DEFAULT FALSE,     -- 是否已处理
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_server_command_received_time ON server_command_received(msg_time);
CREATE INDEX IF NOT EXISTS idx_server_command_received_processed ON server_command_received(processed);
```

##### 4. `server_command_sent` - serverCommand 流发送的响应

```sql
CREATE TABLE IF NOT EXISTS server_command_sent (
    msg_id TEXT PRIMARY KEY,
    msg_time INTEGER NOT NULL,           -- 消息时间戳（毫秒）
    msg_type TEXT NOT NULL,              -- 消息类型：COMMAND_STATUS_UPDATE, TASK_PROGRESS_UPDATE 等
    robot_id TEXT NOT NULL,
    command_id TEXT,                     -- 关联的命令ID（可选）
    data_json TEXT NOT NULL,             -- 响应数据 JSON
    status TEXT DEFAULT 'sent',          -- 状态：pending, sent, ack, failed
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_server_command_sent_time ON server_command_sent(msg_time);
CREATE INDEX IF NOT EXISTS idx_server_command_sent_type ON server_command_sent(msg_type);
CREATE INDEX IF NOT EXISTS idx_server_command_sent_command_id ON server_command_sent(command_id);
```

### 2.3 消息类型对照表

| 消息类型 | 所属表 | 发送函数 |
|---------|--------|---------|
| ROBOT_STATUS | client_upload_sent | `_report_robot_status()` |

| TASK_PROGRESS_UPDATE | server_command_sent | `_send_task_progress_update()` |
| OPERATION_RESULT | server_command_sent | `_send_operation_result()` |

## 三、修改方案

### 方案 A：最小改动方案（推荐先行）

仅修复 `robot_sent_messages` 为空的问题，不涉及表结构变更。

#### 修改内容

**文件**: `RobotControlSystem.py`

在以下 4 个函数中添加 `save_sent_message()` 调用：

##### 1. 新增辅助方法

```python
def _save_server_command_message(self, msg_id: str, msg_time: int, msg_type: str, data: dict):
    """保存通过 serverCommand 流发送的消息到数据库

    Args:
        msg_id: 消息唯一标识
        msg_time: 消息时间戳（毫秒）
        msg_type: 消息类型
        data: 消息数据字典
    """
    try:
        self.task_manager.database.save_sent_message(
            msg_id=msg_id,
            msg_time=msg_time,
            msg_type=msg_type,
            robot_id=self.robot_id,
            data_json=json.dumps(data, ensure_ascii=False),
            status='sent'
        )
    except Exception as e:
        self.logger.error(f"保存 serverCommand 消息到数据库失败: {e}")
```

##### 2. 在 4 个发送函数末尾添加保存调用

- `_send_command_status_update()` - 添加消息保存
- `_send_set_marker_response()` - 添加消息保存
- `_send_task_progress_update()` - 添加消息保存
- `_send_operation_result()` - 添加消息保存

## 六、结论

1. **确认废弃**：`tasks` 和 `station_tasks` 表已废弃（`save_task()` 被注释），相关代码可删除

2. **推荐实施顺序**：
   - 先实施**方案 A**，快速解决 `robot_sent_messages` 为空的问题
   - 再清理废弃的 `tasks` 和 `station_tasks` 表
   - 最后按需实施四表重构

3. **四表设计优势**：
   - 按数据流分离，职责清晰
   - 便于按流/方向单独查询和统计
   - 避免混用导致的查询复杂性
