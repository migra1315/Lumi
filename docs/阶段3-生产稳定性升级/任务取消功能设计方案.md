# 任务取消功能设计方案

> 编制日期：2026-08-27  
> 更新日期：2026-08-28
> 文档状态：步骤一至三已实现并通过多智能体审查与 Mock 验证；真实硬件停止、安全姿态和自动回充待实现
> 协议依据：`gRPC/proto/RobotService.proto` 中的 `CANCEL_TASK_CMD = 10`

## 1. 背景与目标

后台管理系统通过 `serverCommand` 双向流下发任务取消命令。当前机器人端已经完成协议解析、等待任务取消和运行任务协作取消框架；真实 AGV、JAKA 机械臂的受控停止、外部轴状态确认、安全姿态和自动回充仍按后续步骤实施。

本方案目标是：

- 支持取消尚在等待队列中的任务；
- 支持取消正在执行的任务；
- 正确停止 AGV 和机械臂动作；
- 对短时间原子操作采用“完成当前操作后停止”；
- 外部轴没有运行中停止能力，按不可中断的短操作处理；
- 完成取消后，如果没有新的任务，机器人自动返回充电；
- 向后台仅反馈本次取消请求“取消成功”或“取消失败”的最终结果；
- 保证重复取消、完成与取消竞态、断线重发时的幂等性。

## 2. 已确认的业务规则

### 2.1 取消等待队列中的任务

如果目标任务已经入队但尚未执行：

1. 阻止该任务进入执行流程；
2. 可以从队列中安全移除，或者保留在队列中并在出队时通过取消检查点跳过；
3. 将原任务命令、任务及未执行站点标记为已取消；
4. 不调用任何硬件停止接口；
5. 取消完成后检查是否还有新的可执行任务；
6. 如果没有新的任务，则进入自动回充流程。

实现上优先采用“任务注册表 + 取消标记 + 出队检查”。Python `PriorityQueue` 没有稳定的按条件删除接口，直接操作其内部数组会增加并发风险。即使为了及时释放队列而实现移除，也必须保留出队取消检查作为第二道保护。

### 2.2 取消正在执行的任务

如果目标任务正在执行：

1. 设置该任务的线程安全取消标志；
2. 停止当前 AGV 动作；
3. 停止当前机械臂动作；
4. 短时间原子操作可以执行完成，但完成后不得进入后续任务阶段；
5. 外部轴没有运行中中断停止逻辑，取消时允许当前外部轴动作完成，返回后立即终止后续流程；
6. 确认执行线程退出、硬件停止并完成取消请求结果和审计记录落盘；
7. 立即将机械臂移动到预先配置并经过现场验证的固定安全姿态，具体关节数据待定；
8. 安全姿态到位后，才向后台反馈取消成功；若安全姿态恢复失败，则反馈取消失败并禁止自动回充；
9. 取消完成后检查等待队列；
10. 如果没有新的任务，在满足移动安全条件后返回充电。

任务取消属于受控中止，不等同于急停。除非受控停止失败并满足独立的安全策略，否则不得用急停代替普通任务取消。

## 3. 管理端下发协议

管理端当前约定继续复用 `Task` 消息，只填写目标任务 ID：

```protobuf
ServerStreamMessage {
    command_id: <本次取消请求的命令ID>
    command_type: CANCEL_TASK_CMD
    robot_id: <目标机器人ID>
    task_cmd {
        task_id: <需要取消的任务ID>
    }
}
```

两个 ID 的语义必须严格区分：

| 字段 | 含义 |
|---|---|
| `ServerStreamMessage.command_id` | 本次取消操作自己的命令 ID，用于幂等、审计和反馈取消操作结果 |
| `ServerStreamMessage.task_cmd.task_id` | 被取消的业务任务 ID |

机器人端不得把只包含 `task_id` 的 `task_cmd` 当作完整任务解析。收到消息后应转换成内部专用模型：

```python
@dataclass
class CancelTaskCmd:
    task_id: int
```

必须校验：

- `command_type == CANCEL_TASK_CMD`；
- `data_json` 的实际 oneof 字段是 `task_cmd`；
- `task_cmd.task_id > 0`；
- 外层 `robot_id` 与当前机器人匹配；
- `command_id` 未被处理，或者属于可幂等重放的重复请求。

```text

StationTaskStatus.CANCELLED = "cancelled"
```

保留 `SKIPPED` 兼容旧数据，但新取消流程统一使用 `CANCELLED`。

### 4.5 任务状态持久化边界

后台管理端是业务任务生命周期的主数据源，机器人重启后不要求恢复或续跑重启前的任务。因此第一版不新增完整的 `tasks`、`task_stations` 状态表，也不以机器人本地任务状态作为后台业务状态的替代来源。

机器人端仍需保存以下最小必要信息：

- 取消请求命令及其 `command_id`、目标 `task_id`、处理结果，用于断线重发幂等和审计；
- 原任务对应的统一命令终态及必要元数据；
- 任务和站点取消过程的本地历史日志；
- 当前进程运行期间的任务、站点 `CANCELLED` 内存状态，用于阻止后续阶段和错误重试。

重启时不恢复 `QUEUED` 或 `RUNNING` 任务，也不自动继续取消前的业务动作；残留的非终态命令应按“执行已中断”完成本地收敛，等待后台根据自身任务状态重新决策。若后台重发相同取消 `command_id`，机器人应优先读取已保存的取消请求结果；如果取消过程在结果落盘前中断，则不得凭空判定成功。第一版对外只有成功/失败，因此按取消失败处理并记录详细本地原因。

## 5. 总体处理链路

```text
后台下发 CANCEL_TASK_CMD
    ↓
Proto 转换器只解析目标 task_id
    ↓
RobotControlSystem 保存接收记录并做即时分流
    ↓
TaskManager 创建并保存“取消请求命令”
    ↓
TaskScheduler 根据 task_id 查找目标任务
    ├─ 等待队列中 → 标记取消，出队时跳过
    ├─ 正在执行中 → 设置 cancel_event，停止当前硬件动作
    ├─ 已取消 → 幂等成功
    ├─ 已完成/已失败 → 拒绝取消
    └─ 不存在 → 取消失败
    ↓
工作线程在安全检查点退出
    ↓
原任务及未执行站点标记 CANCELLED
    ↓
运行中任务：机械臂恢复到固定安全姿态
    ↓
仅反馈取消请求的最终结果：COMPLETED 或 FAILED
    ↓
原子检查是否存在新的可执行任务
    ├─ 有 → 调度下一任务
    └─ 无 → 满足安全前提后入队自动回充命令
```

## 6. 取消命令的调度方式

取消命令不能进入现有普通优先级队列等待执行。当前调度器在 `current_command` 结束前不会取下一条命令，即使取消命令拥有最高优先级，也会在原任务完成后才运行。

推荐处理方式：

1. `RobotControlSystem` 识别 `CANCEL_TASK_CMD` 后即时分流；
2. 调用 `TaskManager.request_cancel_task(cancel_command_id, task_id)`；
3. 该方法快速登记请求并设置取消标志，不向管理端发送中间状态；
4. 不在 gRPC 接收线程中长时间等待硬件停止；
5. 目标任务退出并完成必要的安全姿态恢复后，由调度器回调发送唯一一次最终反馈。

取消请求本身需要保存为独立命令，但不进入单线程业务执行器。

## 7. 调度器数据结构

建议增加线程安全的活动任务注册表：

```text
task_id → UnifiedCommand
task_id → threading.Event
task_id → cancel_request_command_id
task_id → lifecycle state
```

所有读写通过专用锁保护。至少应提供：

```python
request_cancel_task(task_id, cancel_command_id)
is_task_cancel_requested(task_id)
raise_if_task_cancelled(task_id)
finalize_task_cancel(task_id)
has_runnable_task()
```

不要只依赖数据库查找活动任务，因为数据库状态与当前工作线程之间存在时间窗口；也不要通过遍历 `PriorityQueue` 的内部字段作为唯一真相。

## 8. 等待任务的取消

### 8.1 推荐方式

收到取消请求后：

1. 在活动任务注册表找到目标任务；
2. 确认状态为 `PENDING` 或 `QUEUED`；
3. 设置取消标志；
4. 将内存命令、数据库命令、任务和站点状态更新为 `CANCELLED`；
5. 当该对象后续从优先级队列弹出时，调度器检查终态或取消标志，直接丢弃，不进入执行器；
6. 向管理端仅反馈本次取消请求成功，不额外上报原任务取消状态。

### 8.2 队列清理

可以在锁保护下重建队列以尽快移除取消项，但这是优化，不是正确性的前提。无论是否物理移除，都必须保留：

```python
if command.status == CommandStatus.CANCELLED or cancel_event.is_set():
    skip_command(command)
```

## 9. 运行任务的协作取消

正在执行的命令不能在收到请求时立即被标记为终态。否则调度线程可能清空 `current_command/current_task`，而工作线程仍在运行，随后其他命令会覆盖当前状态指针。

正确顺序：

```text
目标任务保持 RUNNING
    ↓
设置 cancel_event
    ↓
请求当前硬件受控停止
    ↓
工作线程在检查点抛出 TaskCancelledError
    ↓
原任务命令终态及取消审计记录落盘；任务和站点在当前进程内标记为 CANCELLED
    ↓
调度器保持当前硬件执行权，禁止放行下一任务
    ↓
机械臂恢复到固定安全姿态
    ├─ 成功 → 反馈取消成功，释放调度执行权
    └─ 失败 → 反馈取消失败，进入故障/人工处理，不调度新任务
```

建议通过专用 `TaskCancelledError` 或显式执行结果区分取消与失败。`_command_execution_done()` 必须单独处理取消，禁止：

- 将取消覆盖为 `COMPLETED`；
- 将取消覆盖为 `FAILED`；
- 对取消任务执行自动重试；
- 在取消后继续执行复位或后续站点。

原任务进入 `CANCELLED` 只表示其业务动作已经终止，不代表整个取消请求已经成功。即使后续安全姿态恢复失败，原任务仍保持 `CANCELLED`，但取消请求对外反馈失败；调度器必须保持故障阻塞状态，不能在姿态恢复期间或恢复失败后启动下一任务。

## 10. 取消检查点

任务执行链至少在以下位置调用取消检查：

- 任务开始前；
- 每个站点开始前；
- 站点每次重试前；
- 重试等待期间；
- AGV 动作开始前和返回后；
- 外部轴动作开始前和返回后；
- 机械臂动作开始前和返回后；
- 开门、关门、拍照、服务等操作开始前和返回后；
- 机械臂和外部轴复位前；
- 任务结果汇总前。

短操作收到取消时允许完成当前调用，但调用返回后必须检查取消标志，不能进入下一阶段。

## 11. 硬件停止策略

### 11.1 AGV

使用现有 `/api/move/cancel` 接口停止当前移动任务。需要同步修改 AGV 移动等待循环：

- 周期检查任务取消标志；
- 识别 `canceled`、`cancelled`、`idle` 等取消后的实际状态；
- 避免取消后仍只等待 `succeeded/failed` 而永久阻塞；
- 确认取消接口成功后，再确认 AGV 已停止。

### 11.2 机械臂

JAKA SDK 提供 `motion_abort()` 用于终止当前运动。当前封装使用阻塞式 `joint_move(..., is_block=True)`；为了可靠响应取消，建议改为：

1. 非阻塞下发运动；
2. 周期查询是否到位或运动状态；
3. 每个轮询周期检查 `cancel_event`；
4. 收到取消后调用 `motion_abort()`；
5. 查询确认机械臂已经停止；
6. 将中止结果返回调度器。

JAKA SDK 的非阻塞运动和强制中止基本用法如下：

```python
# 关节增量运动（非阻塞）
robot.joint_move(
    joint_pos=[1, 0, 0, 0, 0, 0],
    move_mode=1,      # INCR
    is_block=False,   # 非阻塞
    speed=0.05
)

print("wait")
time.sleep(2)

print("stop")
robot.motion_abort()  # 强制中断当前运动
```

该示例用于说明 `is_block=False` 和 `motion_abort()` 的配合方式。正式任务代码不能使用固定 `sleep(2)` 判断运动过程，也不能固定使用增量运动模式；现有任务仍应按目标位置选择正确的绝对/增量模式，并通过轮询同时处理到位、取消、超时和 SDK 错误：

```python
ret = robot.joint_move(
    joint_pos=target_joints,
    move_mode=move_mode,
    is_block=False,
    speed=speed,
)
ensure_sdk_success(ret)

while True:
    if cancel_event.is_set():
        abort_ret = robot.motion_abort()
        ensure_sdk_success(abort_ret)
        wait_until_motion_stopped(timeout=stop_timeout)
        raise TaskCancelledError("机械臂运动已中止")

    if is_motion_completed():
        break

    if motion_timeout_reached():
        robot.motion_abort()
        raise MotionTimeoutError("机械臂运动超时")

    cancel_event.wait(0.1)
```

其中 `ensure_sdk_success()`、`wait_until_motion_stopped()` 和 `is_motion_completed()` 是设计中的封装方法，不是当前工程已有函数。实现时应根据现场 SDK 版本对 `motion_abort()`、`is_in_pos()` 或运动状态查询的真实返回值进行验证。

### 11.3 外部轴

当前工程只定义了以下外部轴接口：

- `/moveto`；
- `/sysinfo`；
- `/reset`；
- `/enable`；
- `/status`。

已经确认外部轴控制服务没有运行中中断停止逻辑，因此外部轴动作正式按不可中断的短操作处理：

1. 外部轴动作开始前检查取消标志；
2. `/moveto` 已经发出后，不尝试通过急停、失能或未定义接口强行中断；
3. 取消请求保持处理中，等待当前 `/moveto` 调用返回；
4. 调用返回后查询 `/status`，确认外部轴真实状态；
5. 无论该次外部轴动作成功还是失败，都立即检查取消标志；
6. 已请求取消时，不再执行机械臂、操作、复位或后续站点；
7. 当前站点和未执行站点进入取消状态，已经完成的历史站点保持原状态；
8. 外部轴位置不自动回退，回充前由运输安全姿态检查决定是否需要受控恢复。

`/moveto` 请求必须增加合理的连接和读取超时。超时只能避免软件线程永久等待，不代表外部轴已经物理停止；网络超时后如果无法确认外部轴状态，应进入“状态未知/需要人工处理”，不能自动回充。

### 11.4 短时间原子操作

短操作包括但不限于：

- 外部轴移动；
- 开门；
- 关门；
- 单次拍照；
- 短服务动作；
- 已经发出的不可撤销外部设备请求。

这类操作可以执行完成，但返回后必须停止任务。取消不自动执行反向补偿，例如取消开门操作后不应默认再次关门；如业务需要补偿，应使用独立、明确且可审计的恢复策略。

## 12. 安全姿态恢复与自动回充

### 12.1 触发条件

只有同时满足以下条件，才允许生成自动回充命令：

- 目标任务已经进入 `CANCELLED`；
- 当前执行线程已经退出；
- 当前硬件停止结果明确；
- 运行中任务取消后，机械臂已到达配置的固定安全姿态；
- 调度器中没有新的可执行任务；
- 没有新的任务正在并发入队；
- AGV 不处于急停或不可移动状态；
- 机械臂和外部轴位于允许 AGV 移动的运输安全姿态；
- 充电点配置有效；
- 自动回充尚未被其他命令触发。

如果硬件停止失败、外部轴状态未知或机械臂安全姿态恢复失败，本次取消请求反馈失败并进入“需要人工处理”，不能为了满足回充规则继续驱动 AGV。

### 12.2 安全姿态

取消可能发生在机械臂伸出或外部轴非归位状态。运行中任务停止后，应立即执行独立的“恢复运输安全姿态”步骤，先将机械臂移动到固定位置，再结束取消流程：

```text
任务动作停止且工作线程退出
    ↓
查询机械臂和外部轴真实位置
    ↓
确认当前外部轴位置允许机械臂安全运动
    ↓
机械臂移动到配置的固定安全姿态
    ├─ 成功 → 取消成功，随后判断是否需要自动回充
    └─ 失败 → 取消失败，保持静止并告警，不自动回充
```

安全姿态使用绝对关节位置、非阻塞运动和到位确认，具体关节数据待现场验证后填写。参数必须来自配置或经过验证的机器人型号参数，不能散落为调度器中的硬编码位置。还必须结合外部轴当前位置验证机械臂运动路径，不能只验证最终关节位置。

取消等待队列中的任务不会改变当前硬件状态。如果此时另一个任务正在执行，禁止为了被取消的等待任务移动机械臂；如果系统空闲且准备自动回充，则把安全姿态检查与必要的恢复作为回充前置条件。

### 12.3 回充入队方式

自动回充不应直接在取消回调线程中调用 `robot_controller.charge()`，否则可能和调度器并行操作硬件。

应创建内部 `CHARGE_CMD` 并放入统一调度队列，元数据注明：

```json
{
  "source": "auto_charge_after_task_cancel",
  "cancelled_task_id": 123,
  "cancel_command_id": 456
}
```

自动回充命令应使用低于正常任务的优先级，并在真正执行前再次检查队列和当前任务。当前工程中优先级数字越小越高，而默认 `CHARGE_CMD = 4`、`TASK_CMD = 5`，因此自动回充不能直接使用充电命令默认优先级，应显式使用大于 5 的低优先级（例如 9）。这样可以处理“检查为空后、回充执行前又收到新任务”的竞态。

### 12.4 新任务竞态

至少执行两次检查：

1. 取消完成、准备生成回充命令时检查；
2. 自动回充命令真正开始执行前再次检查。

如果第二次检查发现新任务，自动回充命令应标记为跳过或取消，让正常任务优先执行。

如果 AGV 已经开始返回充电后才收到新任务，建议将自动回充也实现为可取消动作：先受控停止回充移动，再按正常调度执行新任务。最终策略需结合现场安全和业务时效测试确认。

### 12.5 充电点配置

当前真实控制器的 `charge()` 使用硬编码点位 `charge_point_1F_6010`。实施时应迁移为配置项，例如：

```json
{
  "charging": {
    "marker": "charge_point_1F_6010",
    "auto_charge_after_cancel": true
  }
}
```

配置缺失或点位无效时，不自动回充，并在机器人本地日志中记录明确原因。

## 13. 状态反馈

管理端不需要机器人恢复状态、后续行为等结构化信息，也不应解析 `message` 字符串。第一版不增加 `CancelTaskResult` 等新消息，只反馈取消成功或取消失败，尽可能降低用户层面和管理端的处理复杂度。

### 13.1 取消请求命令

每个取消请求只发送一条最终 `COMMAND_STATUS_UPDATE`，使用取消请求外层 `command_id`，不发送 `QUEUED` 或 `RUNNING` 中间状态。

取消成功：

```text
ClientStreamMessage.command_type = COMMAND_STATUS_UPDATE
ClientStreamMessage.command_id = <取消请求的 command_id>
CommandStatusUpdate.command_type = CANCEL_TASK_CMD
CommandStatusUpdate.status = COMMAND_STATUS_COMPLETED
CommandStatusUpdate.message = "取消成功"
```

取消失败：

```text
ClientStreamMessage.command_type = COMMAND_STATUS_UPDATE
ClientStreamMessage.command_id = <取消请求的 command_id>
CommandStatusUpdate.command_type = CANCEL_TASK_CMD
CommandStatusUpdate.status = COMMAND_STATUS_FAILED
CommandStatusUpdate.message = "取消失败"
```

具体失败原因只写入机器人本地日志，供排障和审计使用。管理端只依据枚举状态判断结果，不解析 `message`。

### 13.2 成功判定

取消等待队列中的任务，只有在系统能够保证目标任务后续绝不会进入执行器时，才反馈成功。

取消正在执行的任务，只有同时满足以下条件，才反馈成功：

- AGV 和机械臂的可中断动作已经停止；
- 正在执行的外部轴或其他短时间原子操作已经返回；
- 任务工作线程已经退出，不会继续执行后续站点或动作；
- 机械臂已经到达配置的固定安全姿态；
- 原任务命令取消终态、取消请求结果和必要审计记录已经持久化。

原任务、任务和站点仍需在机器人当前进程内使用 `CANCELLED` 状态保证调度正确，但机器人重启后不恢复或续跑这些任务，业务任务最终状态由后台管理端维护。第一版不向管理端额外发送原任务的状态更新。已经完成的站点保持 `COMPLETED`，当前站点和未执行站点记录为 `CANCELLED`，并写入本地历史日志供审计。

### 13.3 失败判定

以下情况反馈取消失败：

- 参数无效、目标任务不存在；
- 目标任务已经 `COMPLETED` 或 `FAILED`；
- AGV 或机械臂停止失败；
- 外部轴调用返回后仍无法确认真实状态；
- 工作线程在限定时间内没有退出；
- 机械臂固定安全姿态恢复失败。

失败时必须保留现场状态和详细本地日志，不得为了返回成功而强行覆盖原任务状态。

### 13.4 结果矩阵

| 目标状态 | 管理端最终反馈 | 内部处理 | 是否检查自动回充 |
|---|---|---|---|
| 等待中且已保证不会执行 | `COMPLETED / 取消成功` | 标记 `CANCELLED` | 是 |
| 执行中且停止、退出、安全姿态均成功 | `COMPLETED / 取消成功` | 标记 `CANCELLED` | 是 |
| 已取消 | 幂等 `COMPLETED / 取消成功` | 保持 `CANCELLED` | 是，但不得重复生成回充命令 |
| 已完成 | `FAILED / 取消失败` | 保持 `COMPLETED` | 否 |
| 已失败 | `FAILED / 取消失败` | 保持 `FAILED` | 否 |
| 不存在 | `FAILED / 取消失败` | 无 | 否 |
| 停止、状态确认、线程退出或安全姿态失败 | `FAILED / 取消失败` | 保留明确故障状态 | 否 |

### 13.5 自动回充与反馈边界

自动回充是取消成功后的机器人内部调度行为，不属于取消结果字段，也不需要向管理端反馈“准备回充”等后续行为。取消成功后即可发送最终结果，无需等待 AGV 到达充电点；随后自动回充失败也不追溯修改已经发送的取消成功结果，但必须写入本地日志并进入相应的设备告警或人工处理流程。

## 14. 幂等与并发

### 14.1 重复取消请求

相同 `command_id` 重发时不得重复停止硬件或重复生成回充命令，应返回第一次处理结果。

不同 `command_id` 取消同一任务时：

- 第一个请求负责实际取消；
- 后续请求关联到同一个取消过程；
- 目标最终取消成功时，后续请求可以幂等成功；
- 自动回充只能生成一次。

### 14.2 完成与取消同时发生

最终状态更新需要在同一个锁保护下完成。推荐规则：

- 若任务完成终态先提交，取消失败；具体原因写入本地日志，对外仍只返回“取消失败”；
- 若取消请求先登记且任务尚未提交完成终态，后续执行路径按取消结束；
- 数据库、内存状态和回调顺序必须一致。

### 14.3 新任务与回充同时发生

“队列为空”和“生成自动回充命令”必须作为受锁保护的调度决策，并在回充执行前再次验证。不能仅调用一次 `queue.empty()` 后直接驱动 AGV。

### 14.4 任务 ID 唯一性

同一机器人当前运行周期内，未进入终态的 `task_id` 必须唯一。收到相同 `task_id` 的新任务时，应拒绝重复入队或幂等关联到原任务，不能覆盖活动任务注册表。一个活动业务任务只关联一个原始 `TASK_CMD command_id`，取消请求则使用自己独立的 `command_id`。

任务进入终态并从活动注册表清理后，历史状态由后台管理端维护；机器人本地只保留统一命令、取消请求结果和审计记录，不承担跨重启的业务任务恢复。

## 17. 测试清单

### 17.1 协议测试

- 管理端只填写 `task_cmd.task_id` 时能够正确解析；
- 缺少 `task_cmd`、`task_id=0`、机器人 ID 不匹配时拒绝；
- 新旧 Proto 生成文件与管理端互通；
- 取消命令类型不会降级为 `RESPONSE_CMD`。
- 每个取消请求只回传一条终态消息，不发送 `QUEUED` 或 `RUNNING`；
- 成功只回传 `COMMAND_STATUS_COMPLETED / 取消成功`；
- 失败只回传 `COMMAND_STATUS_FAILED / 取消失败`；
- 不额外回传原任务的取消状态，管理端不解析 `message`。

### 17.2 队列测试

- 取消第一个等待任务；
- 取消队列中间任务；
- 取消最后一个等待任务；
- 取消后出队不会执行任何硬件动作；
- 已取消对象残留在物理队列时仍会被检查点跳过；
- 队列有其他任务时不会自动回充；
- 队列为空时只生成一次自动回充。

### 17.3 运行取消测试

- AGV移动期间取消；
- 机械臂移动期间取消；
- 运行中任务停止后，机械臂立即移动到配置的固定安全姿态；
- 机械臂安全姿态恢复失败，取消请求反馈失败且不自动回充；
- 外部轴移动期间取消：允许当前移动结束，确认状态后不再执行后续阶段；
- 站点重试等待期间取消；
- 开门、关门、拍照等短操作期间取消；
- 站点完成与取消同时发生；
- 任务最终完成与取消同时发生；
- 取消后不再执行下一个站点；
- 取消后不进入命令失败重试。

### 17.4 自动回充测试

- 取消后队列为空且姿态安全，进入回充；
- 取消后仍有任务，不进入回充；
- 生成回充后、执行前收到新任务，跳过回充；
- 回充途中收到新任务，按最终确认策略受控停止回充；
- 机械臂或外部轴姿态不安全，不移动 AGV；
- 安全姿态恢复失败，不回充并告警；
- 充电点配置缺失，不回充并记录本地原因；
- 回充失败不会重新执行被取消任务。

### 17.5 幂等与重启边界测试

- 相同取消 `command_id` 重发；
- 不同取消命令同时取消同一任务；
- 断线重连后重复收到取消命令；
- 取消过程中服务停止或控制器断电；
- 重启后不会恢复被取消任务；
- 结果落盘前中断的取消请求，重发时不会被错误判定为成功；
- 重启后不会重复生成多个自动回充命令。

## 18. 已确认的硬件取消边界

| 硬件或操作 | 取消策略 | 取消完成条件 |
|---|---|---|
| AGV移动 | 调用 AGV 移动取消接口 | 查询确认 AGV 已停止 |
| JAKA机械臂运动 | 非阻塞运动期间调用 `motion_abort()` | SDK确认运动已停止 |
| 外部轴移动 | 不支持运行中停止，作为短操作完成 | 当前调用返回并查询到明确状态 |
| 开门、关门、拍照等短操作 | 当前原子操作完成后停止后续流程 | 操作返回并到达取消检查点 |

真实机器人验收时必须分别验证：

- AGV取消后的真实状态值和退出时延；
- 当前现场 JAKA SDK 中非阻塞运动、`motion_abort()` 和运动停止查询的返回值；
- 外部轴 `/moveto` 的最大执行时间、请求超时和 `/status` 最终状态；
- 各硬件取消后能否安全进入运输姿态和自动回充。

不得只根据 Mock 测试宣布运行中任务取消功能完成。
