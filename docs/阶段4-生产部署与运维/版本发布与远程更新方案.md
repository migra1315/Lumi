# 版本发布与远程更新方案

> 编制日期：2026-08-27  
> 适用平台：Windows 机器人控制器  
> 文档状态：方案基线，尚未实施  
> 关联文档：[生产部署、代码保护与运维方案](./生产部署、代码保护与运维方案.md)

## 1. 背景

当前主要通过 ToDesk 远程进入机器人控制器，再手工替换一个或多个 `.py` 文件。这种方式在短期调试时很直接，但随着代码量和机器人数量增加，会产生以下问题：

- 开发机与机器人上的代码进度不一致；
- 无法准确回答机器人当前运行的是哪个提交；
- 容易漏传关联文件或传入未完成版本；
- 本地配置、数据库和日志可能在替换时被覆盖；
- Python 依赖和厂商 DLL 不会随代码同步；
- 出现故障后无法快速恢复上一完整版本；
- 多台机器人可能形成互不相同的现场分支；
- 操作过程缺少记录，难以追溯谁在何时更新了什么。

ToDesk 应保留为现场诊断和应急恢复通道，但不再作为正常的软件发布通道。

## 2. 当前仓库状态

截至文档编制时，仓库具备 GitHub 远端，但发布管理仍有以下缺口：

- 当前开发分支为 `feat/ju`；
- 尚未建立正式版本标签；
- 尚未区分稳定生产分支与日常功能分支；
- 尚未生成可安装的版本化发布包；
- 尚未建立自动测试、打包和 Release 流程；
- 尚未实现机器人端更新器；
- 现场配置文件仍与源码仓库存在耦合。

因此当前不建议让机器人直接对 `feat/ju` 执行 `git pull`。

## 3. 目标

将现场更新模式从“同步源文件”改为“安装完整发布版本”：

```text
功能分支开发
    ↓
合并到 main
    ↓
创建 v1.2.0 版本标签
    ↓
自动测试、打包和生成清单
    ↓
发布完整软件包
    ↓
机器人下载并校验
    ↓
进入安全状态并停止服务
    ↓
安装新版本并切换
    ↓
启动与健康检查
    ├─ 成功 → 确认新版本
    └─ 失败 → 自动回滚
```

最终应满足：

- 机器人不保存用于日常开发的 Git 工作目录；
- 每次更新都对应唯一且不可变的版本号；
- 程序、配置、数据库、日志和密钥彼此分离；
- 更新前有安全检查，更新后有健康检查；
- 更新失败可以恢复到上一稳定版本；
- 管理端能够看到每台机器人的当前版本和更新状态；
- ToDesk 只处理自动流程无法处理的异常。

## 4. 版本和分支约定

### 4.1 分支职责

建议采用以下最小分支模型：

| 类型 | 示例 | 用途 | 允许部署到机器人 |
|---|---|---|---|
| 稳定分支 | `main` | 已通过验证、准备发布的代码 | 不能直接部署分支头 |
| 功能分支 | `feat/camera-retry` | 日常功能开发 | 否 |
| 修复分支 | `fix/grpc-timeout` | 缺陷修复 | 否 |
| 版本标签 | `v1.2.0` | 唯一、不可变的正式发布点 | 是 |

机器人只能安装正式版本标签产生的发布包，不能跟随持续变化的分支。

### 4.2 版本号

使用语义化版本：

```text
主版本.次版本.修订版本
1.2.3
```

- 主版本：存在不兼容的协议、配置或数据库变化；
- 次版本：增加向后兼容功能；
- 修订版本：修复缺陷，不改变主要接口；
- 测试版本：使用 `1.2.0-rc.1`，禁止自动推送到全部生产机器人。

### 4.3 版本信息

程序启动后应能够输出和上报：

- 软件版本；
- Git 提交号；
- 构建时间；
- 配置版本；
- 数据库结构版本；
- 设备型号或发布目标；
- 当前更新通道，例如 `stable` 或 `pilot`。

## 5. 发布包设计

### 5.1 发布物

一个正式版本至少包含：

```text
RobotControlSystem-1.2.0-win-x64.zip
manifest.json
SHA256SUMS
release-notes.md
RobotControlSystem-1.2.0-win-x64.zip.sig
```

ZIP 包内部建议为 PyInstaller one-folder 产物：

```text
RobotControlSystem-1.2.0\
    robot-control.exe
    _internal\
    vendor\
    VERSION
    migrations\
    config-template\
```

以下内容不得放入发布包：

- 现场 `config.json`；
- 摄像头、机器人或管理端密码；
- 客户端证书私钥；
- `tasks.db`；
- 日志、抓拍图片和诊断数据；
- 开发机虚拟环境；
- GitHub 访问令牌。

### 5.2 发布清单

`manifest.json` 建议包含：

```json
{
  "product": "RobotControlSystem",
  "version": "1.2.0",
  "git_commit": "abc1234",
  "build_time": "2026-08-27T16:00:00+08:00",
  "target": "windows-x64",
  "robot_models": ["model-a"],
  "config_version": 2,
  "database_version": 3,
  "minimum_updater_version": "1.0.0",
  "package": "RobotControlSystem-1.2.0-win-x64.zip",
  "sha256": "<sha256>",
  "restart_required": true
}
```

更新器不能只相信文件名，必须读取清单并验证版本、目标平台、机器人型号、哈希和签名。

## 6. 发布流水线

建议使用 GitHub Actions 或等价 CI 系统：

1. 功能分支提交并运行静态检查、单元测试。
2. 通过评审后合并到 `main`。
3. 在代表性环境执行集成测试。
4. 创建候选标签，例如 `v1.2.0-rc.1`。
5. 在干净的固定版本 Windows 环境中构建。
6. 收集 Python 依赖、厂商 DLL 和资源文件。
7. 生成版本信息、发布清单和 SHA-256。
8. 对 EXE 或整个发布包签名。
9. 上传为草稿 Release，填写变更和兼容性说明。
10. 人工确认真实硬件冒烟测试结果后发布。

发布步骤必须是可重复的，不能依赖开发人员临时复制 DLL 或修改构建机文件。

GitHub Release 可作为初期的软件包存储位置。如果仓库或网络策略不适合让机器人直接访问 GitHub，可以改为公司对象存储、HTTPS 下载服务或现场文件服务器，但发布包格式和更新协议保持不变。

## 7. 第一阶段：一键更新脚本

第一阶段不需要立即建设完整 OTA。先提供受控的 PowerShell 更新入口：

```powershell
.\update.ps1 -Version 1.2.0
```

此命令代表目标操作，脚本尚未实现。脚本应自动完成：

1. 获取指定版本清单和发布包；
2. 校验下载是否完整；
3. 验证发布包签名和版本兼容性；
4. 检查磁盘空间、服务状态和机器人任务状态；
5. 请求机器人进入安全更新状态；
6. 备份配置、数据库和当前版本信息；
7. 停止 `RobotControlSystem` 服务；
8. 解压到新的版本目录；
9. 执行受控的配置或数据库迁移；
10. 切换 `current` 到新版本；
11. 启动服务并等待健康检查；
12. 成功则确认版本，失败则回滚；
13. 写入更新日志并上报结果。

这一阶段仍可以通过 ToDesk 执行命令，但不再手工判断和替换文件。

### 7.1 建议命令

```powershell
# 查看当前和可用版本
.\update.ps1 -Check

# 安装指定正式版本
.\update.ps1 -Version 1.2.0

# 仅下载和预检，不安装
.\update.ps1 -Version 1.2.0 -StageOnly

# 回滚到上一个已确认版本
.\update.ps1 -Rollback

# 输出最近一次更新结果
.\update.ps1 -Status
```

脚本必须支持非交互执行，并使用明确的退出码表示成功、预检失败、安装失败、健康检查失败和回滚失败。

## 8. 第二阶段：独立更新服务

远程全自动更新需要一个独立于机器人控制服务的 `RobotUpdater`：

```text
RobotUpdater 服务
    ├─ 查询或接收目标版本
    ├─ 下载与校验发布包
    ├─ 检查安全更新条件
    ├─ 停止 RobotControlSystem
    ├─ 安装并切换版本
    ├─ 启动和检查健康状态
    └─ 上报成功、失败或回滚结果
```

更新器必须独立，原因是被更新的程序不能可靠地替换自己正在使用的 EXE、DLL 和服务配置。

更新器应尽量保持小而稳定，不与机器人控制业务共享复杂依赖。更新器自身升级应使用单独流程，不能与业务程序升级同时进行。

### 8.1 下载方式

Windows 可使用 BITS 进行后台下载，以支持断线续传、重启恢复和带宽自适应。也可以使用带 Range 支持的 HTTPS 客户端，但必须具备：

- 超时与重试；
- 断点续传；
- 临时文件和最终文件分离；
- 下载完成后的哈希和签名验证；
- 最大包大小和磁盘空间限制；
- 代理和证书校验策略。

### 8.2 更新来源

优先级建议：

1. 管理端签发的短期下载 URL；
2. 公司内部 HTTPS 发布服务；
3. 私有对象存储；
4. GitHub Release。

不建议在机器人上保存具有仓库写权限的个人访问令牌。如果必须读取私有 Release，只授予设备最小、只读、可吊销的凭据，并存入 Windows 凭据存储。

## 9. 管理端远程更新

管理端不应通过现有 gRPC 流直接传输大型 ZIP。更合适的方式是下发版本意图和下载信息，机器人通过独立 HTTPS 通道下载。

概念消息如下：

```json
{
  "command_id": "update-20260827-001",
  "target_version": "1.2.0",
  "channel": "stable",
  "download_url": "https://example/releases/1.2.0/package.zip",
  "manifest_url": "https://example/releases/1.2.0/manifest.json",
  "not_before": "2026-08-27T22:00:00+08:00",
  "deadline": "2026-08-28T02:00:00+08:00",
  "require_idle": true
}
```

这是方案示例，不表示当前 Proto 已定义这些字段。正式实现时应增加对应消息或管理 API，并进行身份认证、授权和重放保护。

管理端需要展示：

| 字段 | 说明 |
|---|---|
| 当前版本 | 机器人实际运行并通过健康检查的版本 |
| 目标版本 | 管理端期望机器人安装的版本 |
| 更新通道 | `pilot`、`stable` 等 |
| 更新阶段 | 下载、预检、等待空闲、安装、验证、成功、回滚 |
| 下载进度 | 已下载大小和百分比 |
| 最近错误 | 错误码和脱敏说明 |
| 上次成功时间 | 最近一次成功升级时间 |
| 上一稳定版本 | 可回滚目标 |

## 10. 更新状态机

建议使用明确状态机，避免断电后不知道处于哪个步骤：

```text
IDLE
  → CHECKING
  → DOWNLOADING
  → VERIFYING
  → STAGED
  → WAITING_FOR_SAFE_STATE
  → INSTALLING
  → STARTING
  → HEALTH_CHECKING
  ├─ SUCCEEDED
  └─ ROLLING_BACK
       ├─ ROLLED_BACK
       └─ RECOVERY_REQUIRED
```

每次状态变化写入独立更新数据库或原子状态文件。控制器断电重启后，更新器必须能够判断：

- 发布包是否下载完整；
- 当前指针是否已经切换；
- 数据库迁移是否完成；
- 新服务是否启动过；
- 是否应该继续验证或执行回滚。

## 11. 更新前安全条件

机器人软件升级属于影响控制能力的高风险操作。至少检查：

- 当前没有运行中的任务；
- 不存在结果未知且可能重复执行的命令；
- AGV 已停车；
- 机械臂位于允许升级的安全位置，或保持硬件安全互锁；
- 相机和传感器停止不会影响正在执行的流程；
- 电源稳定，移动设备电量达到阈值；
- 与管理端完成任务状态对账；
- 数据库能够备份且磁盘空间足够；
- 发布包适用于当前机器人型号；
- 操作时间位于允许的维护窗口；
- 有可用的上一稳定版本。

如果任一关键条件不满足，更新器应进入等待或拒绝状态，不能强行停止业务进程。

急停、安全 PLC、限位和硬件互锁必须独立于软件更新流程。

## 12. 安装和原子切换

发布目录采用只增不改的版本结构：

```text
releases\
    1.1.0\
    1.2.0\
current\
previous-version.json
```

新版本先完整解压到暂存目录并校验，不能边下载边覆盖当前版本。推荐流程：

1. 解压到 `releases/.staging-1.2.0`；
2. 验证目录文件清单；
3. 将暂存目录重命名为 `releases/1.2.0`；
4. 记录当前版本为回滚目标；
5. 停止服务；
6. 原子更新 `current` 指针或服务可执行路径；
7. 启动服务。

如果使用 Windows 目录联接或符号链接，需要在代表性控制器上验证服务账号权限和切换行为。也可以让服务包装器启动一个固定的 launcher，由 launcher 读取 `current-version.json` 后启动对应版本。

## 13. 健康检查与确认

新进程能够启动不代表升级成功。建议分层验证：

### 13.1 基础检查

- Windows 服务处于 `RUNNING`；
- 进程未在短时间内反复退出；
- 数据库可打开并完成必要迁移；
- 配置版本可被读取；
- 日志目录可写。

### 13.2 通信检查

- gRPC 通道连接成功；
- 双向流建立；
- 心跳正常；
- 管理端收到新版本号和启动事件。

### 13.3 硬件检查

- 机器人、相机和环境传感器状态能够查询；
- 不要求在健康检查中执行实际运动；
- 硬件初始化失败时区分关键组件和可降级组件；
- 系统保持安全、非运动状态。

健康观察窗口内出现崩溃、数据库不兼容或关键通信失败，应触发回滚。

## 14. 回滚

回滚必须是升级流程的一部分，而不是现场出故障后临时复制旧文件。

触发条件包括：

- 服务无法启动；
- 服务反复崩溃；
- 健康检查超时；
- 配置或数据库迁移失败；
- 管理端在观察窗口内拒绝确认；
- 操作人员主动回滚。

回滚流程：

1. 停止新版本服务；
2. 保存新版本日志、转储和更新状态；
3. 恢复兼容的配置和数据库状态；
4. 切换到上一稳定版本；
5. 启动旧版本并执行健康检查；
6. 上报回滚原因和结果；
7. 阻止同一失败版本自动重复安装。

数据库迁移优先采用扩展式、向后兼容变更。如果数据库升级后旧版本无法运行，该版本不能宣称支持自动回滚，必须采用更严格的维护窗口和备份恢复方案。

## 15. 签名和凭据

SHA-256 可以发现下载损坏，但如果攻击者同时替换发布包和哈希文件，不能证明发布者身份。正式版本应使用独立签名密钥：

- CI 生成哈希和待签名产物；
- 受控环境使用代码签名证书签名；
- 机器人仅保存用于验证的公钥或信任链；
- 更新器先验签，再停止机器人服务；
- 签名失败的发布包直接删除并告警；
- 签名密钥不能存放在机器人或源码仓库。

下载凭据与发布签名是两套能力：下载凭据决定“能否取得文件”，签名决定“文件是否由可信发布者产生”。二者不能互相替代。

## 16. 为什么不直接在机器人上 Git Pull

`git pull` 可以作为短期过渡，但不是正式发布机制：

- 分支头会变化，不能代表不可变版本；
- 现场目录可能出现未提交修改和合并冲突；
- Git 不负责 Python 依赖和厂商 DLL；
- Git 不管理数据库迁移和配置兼容；
- 拉取成功不表示程序启动和硬件验证成功；
- 缺少原子切换、健康检查和自动回滚；
- 私有仓库需要在机器人上保存访问凭据；
- 源码和运行数据仍可能混在同一目录。

如果过渡期必须通过 Git 更新，应只检出固定标签，不跟踪功能分支：

```powershell
git fetch --tags
git checkout --detach v1.2.0
```

同时必须保证现场目录没有本地开发修改，配置、数据库和日志位于仓库之外，并在切换前停止服务。该方式应有明确的退出时间表。

## 17. ToDesk 的保留用途

建立更新系统后，ToDesk 仍有价值，但用途调整为：

- 首次安装更新器；
- 查看无法自动上传的现场日志；
- 处理 `RECOVERY_REQUIRED` 状态；
- 修复操作系统、网络或硬件驱动问题；
- 在管理端不可用时执行经过审核的离线更新包；
- 最终应急回滚。

正常版本发布不再依赖打开 ToDesk、寻找目录和手工覆盖文件。

## 18. 分阶段落地计划

### 阶段 A：版本化和一键更新

- 建立 `main` 稳定分支；
- 采用 `vX.Y.Z` 版本标签；
- 建立依赖锁定；
- 生成完整 ZIP 发布包；
- 将配置、数据库和日志移出程序目录；
- 实现 `update.ps1`；
- 支持安装指定版本和手动回滚；
- 仍通过 ToDesk 触发更新。

完成该阶段后，即可消除大部分手工替换文件和版本不一致问题。

### 阶段 B：自动构建和 Release

- GitHub Actions 自动测试；
- 自动构建 PyInstaller one-folder；
- 自动生成清单、哈希和发布说明；
- 建立候选版本和生产版本审批；
- 上传 GitHub Release 或内部发布服务；
- 在真实硬件上记录发布验收结果。

### 阶段 C：机器人端更新器

- 实现独立 `RobotUpdater`；
- 支持断点续传、验签和预检；
- 支持版本目录、原子切换和自动回滚；
- 上报当前版本、进度和错误；
- 支持断电后恢复更新状态机。

### 阶段 D：管理端 OTA

- 管理端维护当前版本和目标版本；
- 支持单机、分组和灰度发布；
- 支持维护窗口和人工审批；
- 支持先试点机器人、后批量推广；
- 自动停止失败版本继续扩散；
- 建立发布和回滚审计。

## 19. 初期推荐决策

结合当前代码规模、Windows 控制器和远程维护方式，建议首先采用：

> `main` 稳定分支 + `vX.Y.Z` 标签 + 完整 ZIP/one-folder 发布包 + `update.ps1` 一键升级 + 上一版本回滚

第一阶段继续通过 ToDesk 执行一条更新命令，不再复制单个 `.py` 文件。验证这套发布包和回滚模型稳定后，再将相同逻辑放入独立更新服务，并接入管理端实现 OTA。

## 20. 验收标准

- 任意机器人均能明确查询当前软件版本和 Git 提交号；
- 同一版本在不同机器人上的程序文件哈希一致；
- 更新时不需要手工选择或覆盖 `.py` 文件；
- 配置、密码、数据库和日志不会随更新包被覆盖；
- 未处于安全状态时更新不会开始；
- 网络中断后下载能够继续或安全重试；
- 发布包损坏或签名错误时不会停止当前服务；
- 新版本启动失败时能够恢复上一版本；
- 回滚后不会自动重新安装同一个失败版本；
- 管理端或更新日志可以追溯更新时间、目标版本、结果和失败原因；
- ToDesk 不再是正常更新必须依赖的步骤。
