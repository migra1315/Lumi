# 生产部署、代码保护与运维方案

> 编制日期：2026-08-27  
> 适用平台：当前以 Windows 机器人控制器为主  
> 文档状态：方案基线，尚未表示全部实施

## 1. 结论

直接手工执行 `python robot_service_runner.py` 适合开发和现场诊断，不适合作为完整的正式部署方式。`robot_service_runner.py` 本身可以继续保留为服务入口；需要改进的是它周围的构建、安装、权限、配置、密钥、升级、回滚和监控体系。

Windows 生产环境的推荐基线为：

> PyInstaller one-folder 或 Nuitka standalone + WinSW/NSSM Windows 服务 + ProgramData 数据目录 + 签名发布包 + 版本化升级与回滚

打包程序只能提高源码查看和修改的门槛，不能替代密钥管理、磁盘加密、通信认证和系统权限控制。

## 2. 当前实现评估

### 2.1 可保留的部分

`robot_service_runner.py` 已经具备服务入口需要的几个基本行为：

- 使用脚本所在目录定位 `conf/config.json`；
- 初始化统一日志；
- 响应 `SIGINT`、`SIGBREAK` 和 `SIGTERM`；
- 停止时通过 `finally` 调用 `robot.shutdown()`；
- 不依赖交互式控制台输入。

因此没有必要为了“看起来更正式”而立即重写成复杂的原生 Windows Service。通过可靠的服务包装器托管仍然是合理方案。

### 2.2 当前缺口

1. 项目没有依赖清单和锁定文件，控制器之间的 Python 和第三方库版本难以保证一致。
2. 源码、配置、数据库和日志没有明确分离，升级容易影响运行数据。
3. `TaskDatabase` 默认使用相对路径 `tasks.db`，日志默认使用相对目录 `logs`，实际落盘位置依赖服务工作目录。
4. 多个 `conf/*.json` 中存在明文设备凭据，并且配置文件处于版本管理范围。
5. gRPC 当前使用 `grpc.insecure_channel()`，缺少传输加密和服务端身份验证。
6. 现有服务控制脚本只负责启停和启动类型切换，没有统一完成安装、权限、恢复策略、升级和卸载。
7. 程序版本、配置版本、数据库结构版本和现场控制器之间缺少可审计的对应关系。

## 3. 目标目录结构

程序文件和可变数据必须分离：

```text
C:\Program Files\<Company>\RobotControlSystem\
    releases\
        1.0.0\
            robot-control.exe
            _internal\
            vendor\
            VERSION
        1.1.0\
    current\
    service\
        RobotControlSystem.exe
        RobotControlSystem.xml

C:\ProgramData\<Company>\RobotControlSystem\
    config\
        config.json
    data\
        tasks.db
    logs\
    secrets\
    update\
    diagnostics\
```

约束如下：

- `Program Files` 中的发布内容安装后只读，运行时不得修改。
- `ProgramData` 保存配置、数据库、日志、升级暂存和诊断包。
- 数据库和日志路径从配置显式传入并转换为绝对路径。
- 新版本安装不得覆盖现场配置、数据库和密钥。
- 每个发布目录包含版本号、构建时间、Git 提交号和文件清单。

## 4. 构建与打包

### 4.1 依赖可复现

至少建立以下一种依赖管理方式：

- `pyproject.toml` 加锁定文件；或
- 固定版本的 `requirements.txt`，必要时附带哈希；
- 面向离线控制器建立经过验证的 wheelhouse；
- 固定 Python 大版本、小版本和 CPU 架构。

构建必须在干净环境中完成，禁止直接把开发机的虚拟环境复制到控制器。

### 4.2 打包选择

优先使用 PyInstaller one-folder：

- 对 OpenCV、gRPC、相机库和厂商 DLL 更容易排查；
- 启动时不需要把全部内容释放到临时目录；
- 杀毒软件误报和临时目录权限问题相对更容易控制；
- 现场可直接检查缺失 DLL 和依赖版本。

如果核心算法需要进一步提高逆向门槛，可评估 Nuitka 或仅使用 Cython 编译核心模块。无论哪种方式，都不能把写在程序里的密码和私钥变成安全秘密。

### 4.3 构建产物要求

每次发布至少生成：

- 版本化程序目录；
- SHA-256 文件清单；
- 软件物料清单或依赖版本清单；
- 配置模板和配置版本说明；
- 数据库迁移及回滚说明；
- 发布说明；
- 安装、升级、回滚和卸载脚本；
- 真实控制器硬件冒烟测试记录。

## 5. Windows 服务托管

### 5.1 服务包装器

WinSW 和 NSSM 均可作为 Python/打包程序与 Windows Service Control Manager 之间的包装层。推荐选择一种并固定版本，不要让现场人员手工配置服务属性。

服务安装配置应进入版本管理，并明确：

- 服务名和显示名；
- 可执行文件和工作目录；
- 配置、数据、日志路径；
- 延迟自动启动；
- 停止超时和停止信号；
- 依赖的系统服务；
- 标准输出、错误输出和轮转策略；
- 服务账号；
- 故障恢复动作。

### 5.2 权限

服务不应无条件以 `LocalSystem` 或管理员账号运行。优先使用独立低权限账号或 Windows 虚拟服务账号，仅授予：

- 读取程序目录；
- 读取配置；
- 读写数据库、日志和诊断目录；
- 访问必要串口、相机和网络资源；
- 作为服务登录。

开发人员、维护人员和服务进程应使用不同权限边界。

### 5.3 故障恢复

建议设置有退避的重启策略，例如第一次 10 秒、第二次 30 秒、第三次 60 秒，并在一天后重置失败计数。不能无限高频重启；连续失败时应保留现场信息并产生告警。

服务进程启动成功不等于系统健康。应另外提供健康状态，至少覆盖：

- 主进程是否存活；
- gRPC 是否连接；
- 数据库是否可读写；
- 机器人、相机和环境传感器是否就绪；
- 最近一次服务端心跳；
- 当前任务和安全状态。

## 6. 配置与密钥

### 6.1 普通配置

普通配置可以保存在 `ProgramData` 的 JSON 中，但应：

- 提供 JSON Schema 或等价校验；
- 包含 `config_version`；
- 启动前校验必填项、类型、地址和范围；
- 保存修改审计和上一个可用版本；
- 日志只输出非敏感配置摘要。

### 6.2 敏感信息

摄像头密码、Token、客户端私钥等不得进入 Git、普通 JSON、命令行参数或日志。Windows 环境可选择：

- Windows Credential Manager；
- 绑定专用服务账号的 DPAPI；
- 企业密钥管理系统；
- 受 ACL 保护的证书私钥存储。

配置文件只保存凭据引用。已经提交到 Git 的凭据应立即轮换；仅删除当前文件中的值并不能消除 Git 历史中的内容。

## 7. 通信安全

机器人控制指令属于高影响操作，不能只依赖“现场网络是内网”。建议分阶段完成：

1. 将 gRPC 从 `insecure_channel` 改为 TLS，并校验服务端证书。
2. 条件允许时启用双向 TLS，为每台机器人分配独立客户端证书。
3. 证书具有机器人身份、有效期、轮换和吊销机制。
4. 服务端按机器人身份授权可执行的命令。
5. 高风险命令包含唯一标识、时效和幂等约束，防止重复执行和重放。
6. 日志不得记录认证 Token、完整证书私钥或带密码的 RTSP URL。

## 8. 源码、防篡改与设备安全

应先明确需要防御的对象：

| 风险 | 主要措施 |
|---|---|
| 现场人员随手查看或误改源码 | 打包为 EXE、程序目录只读、NTFS ACL |
| 程序或 DLL 被替换 | Authenticode 签名、安装时验签、应用白名单 |
| 控制器或硬盘被盗后离线读取 | TPM、Secure Boot、BitLocker |
| 普通用户运行未授权程序 | 标准用户、App Control/WDAC 或 AppLocker |
| 本机管理员逆向核心算法 | 编译核心模块、最小化端侧核心机密、服务端保留可远程执行的敏感逻辑 |
| 凭据从程序或配置中提取 | 独立密钥存储、账号隔离、轮换、短期凭据 |

边缘控制器必须拥有的离线实时控制逻辑无法对本机管理员做到绝对保密。安全目标应是提高逆向成本、发现篡改、缩小泄漏范围并支持凭据吊销，而不是承诺“EXE 无法破解”。

## 9. 升级与回滚

版本发布、更新器设计和管理端远程更新的详细方案参见[版本发布与远程更新方案](./版本发布与远程更新方案.md)。

升级采用版本目录，不直接覆盖当前版本：

1. 下载或导入发布包到暂存目录。
2. 校验签名、哈希、设备型号、系统版本和磁盘空间。
3. 备份配置和数据库，并记录当前运行版本。
4. 请求机器人进入安全状态并停止接收新任务。
5. 停止服务，安装到新的 `releases/<version>` 目录。
6. 执行向前兼容的配置和数据库迁移。
7. 切换 `current`，启动服务并执行健康检查。
8. 健康检查失败则停止新版本、恢复数据兼容状态并切回旧版本。
9. 上报升级结果，保留失败日志和诊断信息。

至少保留当前版本和上一个已验证版本。数据库迁移应尽量采用向后兼容设计；如果无法回滚，必须在发布前明确标记。

## 10. 机器人安全恢复约束

服务自动重启不能直接等价为自动恢复机械动作。进程崩溃、断电或升级后，程序必须先进入安全恢复流程：

- 不自动重复结果未知的机械臂、AGV、门控和拍照动作；
- 读取数据库中的未完成任务，但不能仅凭本地状态决定继续执行；
- 查询各硬件真实状态，并与服务端进行任务对账；
- 使用命令 ID 和幂等机制识别重复命令；
- 对需要人工确认的状态明确阻止自动恢复；
- 物理急停、安全 PLC、限位和硬件互锁独立于 Python 服务；
- 连续启动失败时保持执行器失能或安全状态。

`auto_start_on_boot` 的含义需要细化：允许通信服务自动启动，不应默认意味着所有执行器立即使能并恢复任务。

## 11. 分阶段实施计划

### P0：先消除直接风险

- 轮换已经进入配置和 Git 历史的设备密码；
- 将敏感字段移出普通 JSON；
- 把数据库、日志和配置改为显式绝对路径；
- 固定服务工作目录；
- 建立依赖清单并锁定版本；
- 为 gRPC 启用 TLS；
- 明确断电、崩溃后的安全恢复规则。

### P1：形成标准发布物

- 建立干净、可重复的打包环境；
- 生成 PyInstaller one-folder 发布包；
- 纳入相机、机器人 SDK 和厂商 DLL；
- 建立 WinSW/NSSM 安装配置；
- 使用低权限服务账号和明确 ACL；
- 配置服务恢复策略和健康检查；
- 在代表性真实控制器上做冷启动、断网和重启测试。

### P2：升级、回滚与供应链

- 引入版本目录、签名、哈希和发布清单；
- 实现带预检的一键安装、升级和回滚；
- 建立配置、数据库迁移版本；
- 对接集中监控、日志和升级结果上报；
- 评估 BitLocker、Secure Boot 和 App Control/WDAC。

### P3：持续加固

- 双向 TLS 和设备证书生命周期；
- 软件物料清单和依赖漏洞检查；
- 发布签名密钥的隔离与审计；
- 灰度升级和自动回滚；
- 故障注入、长稳测试和恢复演练。

## 12. 验收标准

达到生产部署基线时，至少应满足：

- 新控制器可以用一个受控安装流程完成部署，无需手工 `pip install`；
- 断电重启后服务自动启动，且机器人保持预期安全状态；
- 停止服务时硬件和后台线程能够在规定时间内退出；
- 程序、配置、数据库和日志路径互不混淆；
- 普通维护账号不能修改程序目录或读取密钥；
- 安装包被修改后无法通过校验；
- 当前版本、构建提交、配置版本和数据库版本可以查询；
- 新版本启动失败时能切回上一稳定版本；
- 网络断开、服务器不可用、相机故障和数据库异常均有可观察状态；
- 日志和诊断包不包含明文密码、Token 或私钥；
- 对结果未知的动作不会在重启后未经确认自动重复。

## 13. 当前推荐决策

在现有 Windows 和 Python 技术栈不变的前提下，建议暂定以下技术决策：

- 保留 `robot_service_runner.py` 作为统一入口；
- 首选 PyInstaller one-folder，真实硬件验证后再决定是否引入 Nuitka；
- WinSW 与 NSSM 二选一，服务配置和二进制固定版本并随发布物交付；
- 运行数据统一迁移到 `ProgramData`；
- 普通配置、敏感凭据、程序文件分开管理；
- 优先修复凭据和 gRPC 安全，再讨论更高强度的源码保护；
- 自动重启必须受机器人安全恢复状态机约束。
